1. Summary and Recommendation#

Preallocating the Raft log alone would not have prevented the incident. Both pods that logged Consensus stopped with error did so with the collection-level disk guard message No space left on device: WAL buffer size exceeds available disk space. That message comes from the local-shard disk-usage check, which runs before a write to a collection WAL. It does not come from the consensus WAL. Consensus stopped because applying a committed entry failed with a service error, and any service error during apply stops the Raft instance.

We recommend a design with three parts. All three are needed for the guarantee below:

  1. 1.
    Reserved consensus storage (R1). The consensus WAL and the Raft state file get fixed-capacity files whose blocks are allocated with fallocate(2) mode 0, overwritten once with zeros and synced while free space still exists. After that, log and state bytes are only written into those ranges. Segments written by an older binary are backfilled in place, without changing any byte that the log can read, before they count as reserve (Section 6.1.1). Retired WAL segments are recycled through a crash-safe staging name instead of being deleted, and no file content changes until the rename that took it out of the log is known durable (Section 6.1.2). Suffix truncation empties the open segment durably, then detaches removed closed segments from the tail down, so every crash leaves a contiguous log (Section 6.1.2.1). raft_state.json and its tmp-file-plus-rename save are replaced by a three-slot file that is overwritten in place, never in a slot that may hold the last acknowledged state, and published through a crash-safe migration (Section 6.1.3). A legacy CBOR state file is first migrated to JSON exactly as today, then from JSON. JSON is never written again once publication has started (Section 6.1.4). A new node also initializes through a durable raft_state.json first and then runs the same migration, so it has the same fallback (Section 6.1.4, "Fresh-node initialization"). If best_effort has to skip migration, the node runs on a JSON backend with its own save sequence and recovery barrier (Section 6.1.5). That node has no reserved state file, so R1 does not hold for it. Likewise, if best_effort cannot materialize WAL segments (fallocate unsupported, or backfill failed), the WAL keeps appending into unreserved space taken from ordinary free space, through a guard that rejects before mutation when it can detect that no space exists (Section 6.5). Unreserved bytes never count as reserve, and R1 does not hold for them.
  2. 2.
    Apply pause instead of consensus stop (R2). If a committed entry fails to apply because of disk-capacity exhaustion, the Raft log and hard state keep being persisted and the node keeps granting votes and acking appends. The state-machine apply cursor stops at the failed entry and retries with backoff. Both the Qdrant apply queue and the raft-rs applied index are held at the last entry that actually applied (Section 6.3.1). No client is told the entry succeeded until it does.
  3. 3.
    Fail-closed on reserve exhaustion (R3). In enforce, when the reserve cannot hold the next append or state save, the node refuses the write before changing any in-memory state, even if ordinary free space exists. In best_effort, an append that does not fit in the reserve may use ordinary free space, and the node refuses it before changing any in-memory state when the guard finds no space (Section 6.5). When a batch replaces a conflicting suffix, the check runs before that truncation, against the layout the truncation will leave, so it neither rejects a batch that fits after the truncation nor guards byte ranges the append will not write (Section 6.5, "Preflight"). A failure that the guard cannot catch, such as a flush error or a process-terminating page fault, never leads to a persisted message (Sections 6.4, 6.5). It sends no persisted messages (votes or append acks) and reloads its Raft state from disk before it rejoins. Reloading alone does not prove durability: after a failed msync/fdatasync, a reopened file can still show bytes that only exist in the page cache. So before the node sends any message again, it runs a recovery barrier that rewrites and re-syncs the recovered log, publishes the recovered state as a new generation into a slot that cannot hold the last acknowledged state, and checks the commit and applied indices against the recovered log (Section 6.4.1). It never skips, drops or acknowledges an entry that was not stored durably.

R1: Reserved consensus storage

Fixed-capacity, fallocated and zero-filled files for the consensus WAL and Raft state; crash-safe recycling, truncation and slot migration.

R2: Apply pause

A committed entry that fails on disk capacity pauses the apply cursor and retries; the log and hard state keep being persisted.

R3: Fail-closed on exhaustion

Refuse the write before changing in-memory state; no persisted message without a durable write; recovery barrier before rejoining.

Guarantee boundary. Stated plainly:

  • What R1 + R2 + R3 aim to provide. On a node in enforce mode, on a filesystem that passes the qualification tests in Section 8 (none is qualified yet, Section 5.4), after ordinary free space reaches zero, a node can keep persisting Raft log entries, hard state and apply progress, and keep participating in Raft as a voter, for as long as its unapplied log fits in the reserve.
  • What best_effort provides. No guarantee. A best_effort node uses its reserve first, in the same placement order, so a node that is not degraded usually behaves like enforce until the reserve runs out. A degraded node (Sections 6.1.1, 6.1.5) has less or no reserve, appends into unreserved space while ordinary free space exists, and goes to R3 when it runs out. On a filesystem without fallocate, its WAL behaves like today's code (off) on the same filesystem, including a possible process-terminating fault on a full disk (Section 6.5). It keeps the same safety rule as enforce: no persisted message for a write that did not complete its flush.
  • What it does not provide. The consensus reserve does not make a collection meta-operation apply succeed. The collection disk guard (shard_ops.rs:83-96) reads ordinary free space, and the reserved blocks are not part of it. Any meta-operation that writes collection data, a collection WAL, segments, or collection config keeps failing until real free space returns. During that time the node's state machine falls behind, proposals that wait for apply time out, and conf changes cannot complete (Section 6.3.4). Collection data, collection WAL, optimizer output, snapshots and segment-state/ID-tracker flushes are not protected.
  • What is not established yet. Section 5.3 lists the filesystem operations that the design still performs on a full disk (renames, directory syncs, inode and journal updates). Linux documents that rename(2) and fsync(2) can fail with ENOSPC. Whether they do so on ext4/XFS after a materialized reserve is in place is an open prototype question (B1, Section 9). Until it is answered, R1 is a "data blocks for log bytes are preallocated" property, not a "no allocation at all" property. The same applies to what a failed directory fsync means for a rename that already returned success: the design treats that rename as "durability unknown" and gates every later step on it (Section 6.1.2), but the filesystem behavior behind it is unverified.
  • Nothing in this document is proven by a test yet. No test in Section 8 has been written or run. Every guarantee above is a design target. It holds only after the prototype passes the tests in Section 8 and the blockers in Section 9 are closed.
  • If a node cannot start because a local shard panics during load (as in the incident from 17:39 onward), no consensus storage design helps that node. Startup robustness is a separate dependency (Section 9).

Open validation and implementation gates (details in Section 9). Revision 12 is conditionally agreed as a design proposal (see "Review Decision"); the gates below are not design-review objections, but questions the prototype must answer before implementation and rollout can proceed: B1 metadata operations (renames, directory syncs) on a full filesystem, including what a failed directory fsync means for a completed rename, and whether rewriting data after a failed msync/fdatasync makes it durable (the recovery barrier, Section 6.4.1); B2 per-operation retry safety after partial effects; B3 raft-rs behavior with the applied index held behind the delivered index for a long time. Each one has a test or audit attached. Section 9 also lists the prototype blockers that must pass before any mode other than off ships.

Alternatives we rejected (Section 6): a sidecar "balloon" file released on failure; relying on ftruncate sizing; ignoring or downgrading persistence errors; and making a dedicated volume the only mechanism. A dedicated volume is a supported option in addition to R1, not a replacement for R2. If B1 shows that metadata operations fail on a full shared volume, a dedicated volume becomes the only way to get the full guarantee, and R1 on a shared volume is downgraded to best effort.

Two points matter:

  • Same crate, different instances. The consensus WAL and collection WALs both use lib/wal/src/segment.rs. A change to the segment allocation code affects both unless it is gated by an option. 4. Durable-Write Trace of a Raft Ready (dev)#

Order inside process_ready (src/consensus.rs:1065-1146) and process_light_ready (:1154-1189):

  1. 1.
    Leader messages are sent before persistence (:1078-1081). raft-rs allows this for leader append messages. Nothing in this design changes it.
  2. 2.
    Snapshot install (:1083-1092 → consensus_manager.rs:757-801) writes collection data (apply_collections_snapshot, :775), then the Raft state (:779), then clears the WAL (:791). Collection data is outside the reserve. A snapshot install while the disk is full fails with a fatal error, as today.
  3. 3.
    WAL append (:1099-1101 → consensus_wal.rs:160-259 → wal/lib.rs:294-308 → segment.rs:336-375): this is a memory copy into an mmap. The in-memory index is updated at segment.rs:373, before the flush. The flush happens at consensus_wal.rs:259 → segment.rs:421-448. flush_offset only advances on success (:446). When the open segment is full, retire_open_segment (wal/lib.rs:265-292) takes the next spare and renames the old one to closed-N (close_segment, :535-546). It may also delete an empty closed segment (:285).
  4. 4.
    Hard state (:1104-1112 → consensus_manager.rs:850-854 → persistent.rs:214-222): the in-memory state is replaced before save(). If the save fails, dirty is set (persistent.rs:405).
  5. 5.
    Persisted messages (votes, append acks) are sent only after steps 3 and 4 succeed (src/consensus.rs:1123-1130). This is the main Raft safety property, and R3 keeps it.
  6. 6.

    Apply. handle_committed_entries (:1229-1240) first calls set_unapplied_entries, which replaces the queue with [first, last] of the delivered batch and rewrites the whole Raft state (persistent.rs:233-240, entry_queue.rs:8-11). It then calls apply_entries (consensus_manager.rs:387-402). Each entry is applied and then followed by entry_applied(), which is another full state rewrite (:489-492, persistent.rs:228-231). A ServiceError from apply_normal_entry returns Err (:448-452) and stops the Raft instance. This is the step that failed in the incident. Two side effects happen inside apply_normal_entry before the handler result is known:

    • the shadow state machine (if enabled) applies the operation first (:627), and apply_entries invalidates it only when apply_entries_impl returns Err (:387-401). The comment at :390-398 says a handler may persist only part of an operation before returning an error, and the state must be reloaded before retry;
    • the proposer's waiter is removed from on_consensus_op_apply and sent the handler's result, including an error (:638, :646-654).
  7. 7.
    Advance. After handle_committed_entries returns Ok, process_ready calls self.node.advance(ready) (:1144) and process_light_ready calls self.node.advance_apply() (:1187) unconditionally. In raft-rs, advance calls advance_apply_to(commit_since_index) (raw_node.rs:663-668), and advance_apply calls commit_apply(commit_since_index) (:712-714). commit_since_index is the index of the last committed entry handed to the application, set when the Ready/LightReady is generated (gen_light_ready, :457-470). So today raft-rs's applied index equals "delivered", not "applied". That is correct only because any apply failure returns Err and the RawNode is dropped.
  8. 8.
    Commit index (:1168-1175 → consensus_manager.rs:875-879): another full state rewrite.
  9. 9.
    Compaction (:1038 → consensus_manager.rs:1109-1136): only compacts up to last_applied_entry, then calls prefix_truncate (wal/lib.rs:410-445). This deletes closed segments.

Rebuild after an error: the failed RaftNode is dropped, but Self::new is passed the same in-memory ConsensusStateRef (src/consensus.rs:198-209). The comment at :170-172 says the rebuild starts "from persisted state", but the in-memory Persistent and ConsensusOpWal (including unflushed WAL index entries from step 3) are reused, not reloaded. The TableOfContent is also reused, so a dev rebuild retries the failed entry in the same process against whatever partial effects the handler left. save_if_dirty (consensus_manager.rs:407-410) covers the Raft state. Nothing does the same for the WAL tail. R3 requires a real reload from disk followed by a recovery barrier (Sections 6.4 and 6.4.1).

5. Physical Reservation: Confirmed Semantics and Open Filesystem Questions#

5.1 Current Behavior#

On Unix, segment creation and growth both use ftruncate:

  • dev: segment.rs:174 (create) and :519 (ensure_capacity)
  • eabee371: :168 and :511

Windows uses fs4 allocate (dev :164-170). The segment is then mapped, and the header (magic wal, version 0, a random CRC seed, :151, 177-182) is written and flushed (:188). The tmp- file is then renamed into place (:198). Segment::open rejects a file whose first three bytes are not the magic with Illegal segment header (:254-256). Wal::with_options fails to open if any open-* or closed-* file fails Segment::open (wal/lib.rs:548-581, the ? at :170), deletes tmp-* files (:564-567) and ignores other names (:582).

5.2 Confirmed Linux Semantics (Primary Sources)#

Quotes were checked against the man7.org pages listed in Section 10.

  • ftruncate(2): if the file was shorter, "the extended part reads as null bytes ('\0')". The page says nothing about disk blocks. Logical size is not a reservation.
  • fallocate(2) mode 0: "allocates the disk space within the range specified by offset and size". "Any subregion within the range specified by offset and size that did not contain data before the call will be initialized to zero." "After a successful call, subsequent writes into the range specified by offset and size are guaranteed not to fail because of lack of disk space." It fails with ENOSPC ("There is not enough space left on the device") at reservation time and with EOPNOTSUPP if "the filesystem ... does not support this operation".
  • posix_fallocate(3): in glibc, if the filesystem does not support fallocate(2), "the operation is emulated", and the emulation is "inefficient" and "not MT-safe". musl returns EOPNOTSUPP instead. We call fallocate(2) directly, through rustix, and treat EOPNOTSUPP as "reservation unsupported" instead of falling back silently.
  • fsync(2): lists ENOSPC "Disk space was exhausted while synchronizing", and ENOSPC/EDQUOT for filesystems that do "not allocate space at the time of a write(2)". It also says fsync of a file "does not necessarily ensure that the entry in the directory containing the file has also reached disk"; an explicit fsync of the directory is needed. fdatasync "does not flush modified metadata unless that metadata is needed" to read the data.
  • rename(2): lists ENOSPC "The device containing the file has no room for the new directory entry" and EDQUOT for the block quota. So a rename can fail on a full disk. The page does not say when a filesystem needs a new block for the entry.
  • msync(2): documents only EBUSY, EINVAL and ENOMEM. It does not document how a writeback failure (EIO, ENOSPC) is reported. memmap2's flush_range, which the WAL uses (mmap_view_sync.rs:122-124), calls msync.
  • mmap(2): documents SIGBUS only for access "beyond the end of the mapped file". It does not document what happens when a store into a hole cannot be backed by a block. Treat the failure mode of a page fault on a full disk as unknown until test T2.

5.3 What fallocate Does Not Cover#

The man page guarantee covers writes into the allocated byte range. The design also depends on things that guarantee does not mention. Each one is labeled.

mmap failure mode. The consensus WAL writes through mmap (segment.rs:352-370). The msync flush (:436) is the only call that can return an error. If a store into a hole cannot be allocated, the failure is likely a page fault that kills the process (for example SIGBUS), not an Err. No cited man page documents this. Test T2 records the behavior. Materialization removes holes from the reserved range, so R1 avoids the case for log bytes either way. The best_effort unreserved path (Section 6.5) can still store into holes. Where fallocate works, its guard allocates the target range before the store. Where fallocate is unsupported, a store can fault, and Section 6.5 treats that fault as a process crash.

6.1.1 Consensus WAL Segments#

  • Add a WalOptions field, for example preallocate: Materialize | Sparse. Collection WALs keep Sparse. ConsensusOpWal::new (consensus_wal.rs:30-46, which uses Wal::open with defaults today) switches to Materialize, and also passes the admission policy, an enum Enforce | BestEffort taken from reserve.mode (Section 6.5). Each segment that the WAL holds (the open segment and pending spares) carries a class: reserved (materialized and durably published, Section 6.1.2 G2) or unreserved (anything else). Only reserved segments count toward reserve capacity.
  • Materialize. Segment::create keeps its structure (segment.rs:137-198): build the segment in tmp-<name>, then rename. In Materialize mode, replace ftruncate with: fallocate mode 0 over [0, C); pwrite zeros over [0, C); write the header; fdatasync the file; rename; fsync the directory. The directory sync is already done by create_segments (segment_creator.rs:53-54). A crash before the rename leaves tmp-*, which Wal::open deletes (wal/lib.rs:564-567). That returns the blocks to the shared pool, but it is safe: no WAL content is lost, and the pool is refilled when space allows.
  • Pool. Keep at least P materialized spare segments. Today segment_queue_len is 0 and is clamped to 1 (wal/lib.rs:37-41, segment_creator.rs:97), and the spare is created on a background thread (segment_creator.rs:107-123). In Materialize mode the pool is created and checked at startup. Refills run in the background, and a refill failure only lowers the reserve-level metric. It never panics the thread and never blocks an append. In enforce, the creator only makes materialized segments. In best_effort, if fallocate returns EOPNOTSUPP, the creator falls back to today's ftruncate creation and the new spare is unreserved. Otherwise a node on a filesystem without fallocate could never retire its open segment. On ENOSPC it does not fall back: no free blocks exist, so a sparse spare's first store would fail, and the refill is retried later.
  • Growth. ensure_capacity (segment.rs:495-526) grows a segment when a single entry is larger than its capacity. In Materialize mode, the WAL must reject such an entry before append mutates the index (R3), and the proposal path must reject entries larger than the configured entry cap E_cap, whose footprint is required to fit in the usable segment capacity U (Section 6.5: the capacity rounded down to 8 bytes, minus the 8-byte segment header), so that growth never happens on the reserved path. Runtime admission still checks every entry against U itself and does not rely on the cap (Section 6.5). All nodes must use the same C: a follower with a smaller C than the leader would have to refuse an entry the leader accepted, and would stay fail-closed (R3) until reconfigured.
  • Segment deletes. Today blocks leave the WAL through prefix_truncate (wal/lib.rs:433, 443), suffix truncation (:367, 381, 396), and removal of an empty closed segment on retire (:285). In Materialize mode, each of these goes through the recycle protocol below instead of delete, so the reserved blocks stay owned by the consensus WAL. Suffix truncation also needs a fixed order across segments, defined in Section 6.1.2.1.

Existing segments on upgrade (backfill). Switching an existing node to Materialize does not create new files for the segments it already has. Wal::with_options reopens every open-* file through Segment::open (wal/lib.rs:169-175): the non-empty one becomes the active open segment, and empty ones become pending spares handed to SegmentCreatorV2::new (:218-245, segment_creator.rs:64-105). Only segments created later go through Segment::create. All the reopened files were sized with ftruncate by the older binary, so their unused tails can be holes. Without a backfill, reserve mode would append into a sparse tail on a full disk, with the unknown mmap failure mode from Section 5.3, even though new spares are materialized.

Backfill runs inside Wal::with_options in Materialize mode, after the directory lock (:163) and before any segment is mapped (:169). For each file it applies to:

  1. 1.
    fallocate mode 0 over [0, file_len) (no FALLOC_FL_KEEP_SIZE needed, the range is inside the file). This allocates blocks for holes and leaves existing data untouched. On an already-allocated range it allocates nothing.
  2. 2.
    Read the file in filesystem-block-aligned chunks (statvfs f_bsize). For each chunk that reads as all zero bytes, pwrite the same zero bytes. Chunks with any non-zero byte are left alone: they already hold written data. This converts holes and unwritten extents in the zero region into written blocks, which is what materialization does for new segments (Section 5.3 row 2). It does not depend on SEEK_HOLE or FIEMAP semantics.
  3. 3.
    fdatasync the file.
  4. 4.
    Verify: parse the segment again (the same logic as Segment::open) and compare the entry count, the last entry offset and the CRC of the last entry with the values recorded before step 1. A mismatch is a bug: refuse to open the WAL in any mode, and leave the file as it is.

Why this preserves the log: step 2 only writes zeros where the file already reads zeros, so every byte the log can read is unchanged at every instant. The CRC chain, the seed in the header, the in-memory index that Segment::open rebuilds, and the result of crash recovery are therefore the same before, during and after backfill. There are no renames and no new files, so a crash at any point leaves a file that reads the same as before. The next start runs backfill again; it is idempotent and only re-reads already-materialized files.

6.1.2 Crash-Safe Segment Recycling#

The earlier draft proposed "zero the header, then rename to open-N". That is unsafe: Segment::open rejects a zeroed header, so a crash could leave an invalid closed-N or open-N that stops Wal::open. There is a second hazard: Wal::with_options treats a non-empty open-N as a written open segment and closes it into the log at the next start index (wal/lib.rs:218-231). An open-N that still parses old entries would inject stale entries into the Raft log.

Invariant: at every durable point, each file named open-* or closed-* is a valid segment whose entries belong to the log at that position, and every recycled open-* parses as empty. Files in transition use a name Wal::open ignores today (wal/lib.rs:582), so older binaries also skip them.

Protocol, for a segment closed-S that prefix_truncate (or another delete site) has already removed from the in-memory segment list:

  1. 1.
    Detach. rename(closed-S, recycle-K), where K is a fresh ID from the segment creator's current_id (strictly greater than the open segment and all pending spares, as SegmentCreatorV2 requires, segment_creator.rs:67-91). fsync the directory.
  2. 2.
    Reset. Allowed only after the directory fsync of step 1 has succeeded (durability gate G1 below). Open recycle-K without mapping it. fallocate mode 0 over [0, C): this is a no-op for a materialized file and materializes a sparse one written by an older binary (Section 6.1.1). pwrite a new header (magic, version 0, a new random seed) at offset 0 and zeros over [8, C). fdatasync the file. The bytes are now identical in form to a fresh Segment::create output. A full overwrite costs one 32 MiB write per recycled segment; it is chosen over zeroing only the first entry because Segment::open (segment.rs:270-288) stops at the first CRC mismatch, and with only a new seed the stale data would still be there and the "parses as empty" property would rely only on a seed change.
  3. 3.
    Publish. rename(recycle-K, open-K), fsync the directory. Hand the segment to the creator's pending list only after that directory fsync has succeeded (durability gate G2 below).

Durability gates. rename(2) is atomic in the namespace: when it returns an error, the rename did not happen, and when it returns success, the new name is visible. Whether the new name survives a crash is only known after a successful directory fsync. If that fsync fails, the rename is in an unknown state: after a crash either name may come back. Two gates follow:

  • G1. No content change before the detach is durable. If step 2 changed the bytes of a file whose rename back to closed-S is still possible, a crash could bring back a closed-S with a reset or torn header. Segment::open would reject a torn header (segment.rs:254-256), and a valid but empty closed-S at the start of the closed list would fail the gap check against the next closed segment (wal/lib.rs:186-207). Either way Wal::open would fail. So step 2 starts only after step 1's directory fsync succeeded.
  • G2. No append before the publish is durable. If entries were appended to open-K while the rename from recycle-K could still be lost, a crash could bring back recycle-K. Wal::open ignores that name, so the appended (and possibly acked) entries would disappear from the log. So the segment is not handed out until step 3's directory fsync succeeded.

If either directory fsync fails, the process marks that file durability unknown and stops touching it: no reset, no hand-out, no delete. It stays under its current name and does not count toward reserve. Per Section 6.4 the WAL handle is then closed and reopened from disk, and the node sends nothing until the recovery barrier (Section 6.4.1) has passed. Because the failed fsync may have dropped the dirty directory state, a later successful fsync in the same process is not used to clear the mark: the set of unknown files is kept in process memory across that reopen, and the reopen skips them (an unknown empty open-* is not added to the spares, an unknown recycle-* is not reset). The next process start runs recovery, which begins with a directory fsync and applies the gates again. Whether a successful directory fsync after an earlier failure (across a restart without a crash) proves the earlier rename durable is part of B1. Until T2c shows it on a qualified filesystem, that recovery step is a design assumption, not a verified property.

Startup directory fsync. In Materialize mode, Wal::with_options fsyncs the WAL directory after taking the lock and before backfill, recycle recovery or the directory scan. If that fails, it returns an error in both best_effort and enforce: no rename seen in the namespace can be trusted, and handing out an open-* spare whose publish is not durable would break G2. Whether this fsync really makes an earlier unknown rename durable is the B1 question above.

Retire rename (open-N → closed-N, close_segment, wal/lib.rs:535-546) is not gated, and needs no gate: both names hold the same valid, non-empty segment, and Wal::with_options already closes a non-empty open-* into the log at the right start index if the rename is lost (:218-231, with the comment at :220-224). A failed or unknown retire rename can therefore never drop a committed prefix. It can leave the in-memory WAL inconsistent, because retire_open_segment swaps in the new open segment before close_segment returns (:267-289). Section 6.4 handles that by reloading the WAL from disk after any append error.

Required ordering checks:

  • Step 1 must not start until the in-memory log no longer references closed-S, which is the same precondition as today's delete.
  • Only a prefix of the closed segments (or the tail removed by suffix truncation) is recycled, so the remaining closed-* set stays contiguous and Wal::open's overlap/gap checks (wal/lib.rs:186-207) still pass. Contiguity must hold at every durable point, not only at the end, which fixes the order of detaches: prefix_truncate detaches head-first (lowest start index first), suffix truncation detaches tail-first (Section 6.1.2.1). In both, a segment's step 1 directory fsync must succeed before the next segment's step 1 starts.
  • WAL-wide detach latch. The per-file durability unknown rule above is not enough when several segments are detached in a row. If segment X's detach is unknown and the next segment's detach is then made durable, a crash can bring X back next to a hole (for prefix_truncate: an unknown c[0] returns while c[1] is durably gone). So the first durability unknown detach, publish or delete in the WAL directory sets a latch in process memory that survives the reload in Section 6.4. While it is set, the WAL refuses, with an error, every structural change: detaches (prefix, suffix, and the retire-time removal of an empty closed segment at wal/lib.rs:281-286), retire renames (a new closed-X could take the name of a file whose detach is unknown), and recycle steps 2 and 3. Appends that fit in the current open segment and open-segment-only truncation (branch A in Section 6.1.2.1) are still allowed. When the open segment fills, the append fails and R3 applies. Only a process restart, which starts with the startup directory fsync, clears the latch. This trades availability for not having to trust a later directory fsync within the process (B1).
  • Entries removed by a suffix truncation were never committed (Raft never truncates committed entries), but they are stale. Step 2 must complete before the segment can reappear as open-*. Until then it is only recycle-*.
  • If step 1's rename returns an error (for example ENOSPC from rename(2)), the rename did not happen, and the code falls back to today's delete of closed-S. That loses reserve but never leaves an invalid file: if the unlink is lost in a crash, closed-S is the "longer prefix" case in the first row. The reserve metric drops, and B1 decides how often this can happen.
  • If step 2's fallocate fails (a sparse segment from an older binary on a full disk), delete recycle-K. G1 already made its detach durable, so the log cannot see it either way. Count it in the recycle fallback metric. A sparse closed segment is therefore never handed out as reserve.
  • If step 3's rename returns an error, leave recycle-K in place for startup recovery. It does not count as reserve.
6.1.2.1 Crash-Safe Suffix Truncation (Wal::truncate)#

Revision 2 only said that "the tail removed by suffix truncation" goes through recycle. Reading Wal::truncate (wal/lib.rs:351-402) shows three reasons that is not enough:

  • Order. In the branches that remove closed segments, the current code drains them from the lowest removed start index upward (drain(index..) at :365, drain(index + 1..) at :379, drain(..) at :394). With durable detaches in that order, a crash after the lowest removed segment is gone but before the higher ones are leaves closed-* files above a hole, and Wal::with_options fails with missing segment(s) containing wal entries (:199-206).
  • The open segment has no start index on disk. open-N carries an ID, not a start index. On restart its first entry is placed right after the last closed segment (:218-237, open_segment_start_index at :449-456). If closed segments are removed while open-N still holds entries on disk, or if new entries become durable in open-N while removed closed segments can still come back, a restart places those entries at the wrong WAL index. ConsensusOpWal derives every Raft index from the first WAL entry (IndexOffset, consensus_wal.rs:351-358, 397-426) and checks wal_index < entry.index only with debug_assert! (:384-390), so a release build would not detect the shift.
  • Truncation zeros are not synced today. Segment::truncate zeros the removed range in the mapping and sets flush_offset = min(flush_offset, zero_start) (segment.rs:411-417). Segment::flush syncs only [flush_offset, size()) (:421-436), and right after a truncate size() == zero_start, so that call syncs nothing. The removed entries disappear on disk only if the kernel writes the pages back on its own, or if a later append overwrites the first removed entry and breaks the CRC chain (segment.rs:268-291). So the boundary flush() at wal/lib.rs:376, and flush_open_segment after clear (consensus_wal.rs:50-51) and truncate_after (:340-341), do not make a truncation durable. The startup check at consensus_manager.rs:128-146 (clear a WAL that still holds entries older than an applied snapshot) already handles one consequence. This is a pre-existing gap in every mode, found by source reading and not yet reproduced (T4f). The design fixes it for Materialize; fixing it for Sparse (collection WALs, and the consensus WAL in off mode) is a separate change (Section 9, risk 12).

New primitive. Segment::truncate_durable(from): the same in-memory change as Segment::truncate, then msync exactly the zeroed range [zero_start, zero_end) before returning Ok. Inside a materialized file this is an overwrite. After it succeeds, Segment::open stops at zero_start, because a zero length with a zero stored CRC is a mismatch (segment.rs:268-286). An msync error is handled as in Section 6.4: the handle is not reused, the WAL is reloaded from disk, and the recovery barrier (Section 6.4.1) must pass before any message is sent.

Algorithm in Materialize mode. Branch A: open.truncate_durable(from - open_start). Nothing is detached. Branches B, C and D, strictly in this order, each step starting only after the previous one returned success:

6.1.3 Raft State Slots#

Revision 4 used two slots, and its recovery barrier rewrote the newest slot G in place. That is unsafe: if G had been saved successfully and acknowledged (a vote, an append ack), a torn rewrite destroys it and leaves only G - 1, which rolls back term, vote or commit. Writing the copy into the other slot instead is unsafe in the opposite case, when G itself is a failed save that only the page cache shows and G - 1 is the last durable state. With two slots there is no write that is safe in both cases. Revision 5 uses three slots and a rule that never overwrites a slot that may hold the last acknowledged state.

  • Replace raft_state.json and AtomicFile (persistent.rs:398-407) with raft_state.slots: a materialized file of fixed size 3 × S_slot holding three slots. Each slot has: magic, format version, a u64 generation (starting at 1; 0 means "none"), a kind (Save or Recovery), a u64 base, a pair of u64 keep generations (Recovery only, 0 = none), payload length, the payload (JSON, the same serde shape as today), and a crc32c over header and payload.
  • Confirmed generation. A generation is confirmed when the fdatasync that followed the full pwrite of its slot returned success, in the process that wrote it. Persisted messages are sent only after the save succeeds (Section 4, step 5), so only a confirmed generation can have been acknowledged. A confirmed slot stays intact on disk until something overwrites it. Persistent keeps confirmed in memory: the newest generation confirmed by this process, or none right after load or after any slot error.

  • Keep set. Every slot write goes to a slot outside a keep set K. K is computed from the slots as read (the view, which can include page-cache bytes that are not on disk, Section 6.4.1). Let N be the newest valid generation in the view:

    • confirmed is set and equals N: K = {N}.
    • Otherwise, N is a Save: K = {N} ∪ {base(N)}, where base(N) is included only if a valid slot holds it.
    • Otherwise, N is a Recovery and every non-zero generation in keep(N) is held by a valid slot: K = keep(N). N itself is not kept.
    • Otherwise, N is a Recovery and some keep(N) generation is missing: K is N plus every keep(N) generation that a valid slot still holds.

    K never has more than two members, so with three slots there is always a target: the slot outside K with the lowest generation, an invalid slot counting as lowest.

  • Save: allowed only when confirmed is set and equals N. After any slot error, R3 and the recovery barrier run first (Sections 6.4, 6.4.1). Serialize the state. If it is larger than S_slot - header, fail before changing anything. Otherwise pwrite the target slot with generation N + 1, kind Save, base = N, then fdatasync. On success, confirmed = N + 1. On failure, clear confirmed. No rename, no new file, no new inode.
  • Recovery write (only from the recovery barrier, Section 6.4.1 step 2): pwrite the target slot with generation N + 1, kind Recovery, keep = K, and the payload of N, then fdatasync. A Recovery generation is never followed by a persisted message. The barrier first saves the same payload again as a normal Save and sends nothing until that Save is confirmed.
  • Load: read all three slots, discard any with a bad magic or CRC, and use the payload of the newest valid generation N. A Recovery slot carries a copy of the payload of the newest generation in its keep (by induction over the rules above), so loading it is the same as loading that generation. Refuse to start, reporting consensus_recovery_blocked, in these cases: no slot is valid and migration is complete (Section 6.1.4); two valid slots hold the same generation; base(N) ≥ N; a keep(N) generation is ≥ N. Each of these is corruption or a bug, and falling back to anything older could roll back term or vote. They need operator action (Section 6.4.1, "Failure").
  • Mutate after save. apply_state_update currently assigns to self.state before save() (persistent.rs:214-222). The new code builds the next state, saves it, and only then assigns it. The same rule applies to entry_applied and set_unapplied_entries, so that in-memory state is never ahead of disk.

Why the loader cannot fall back past an acknowledged generation. Let A be the last acknowledged generation. A was confirmed, so its slot is intact until overwritten. Claim: after any sequence of saves, recovery writes, failures, crashes and restarts, K contains A or a generation whose payload is a copy of a state at least as new as A's, and no write ever targets it.

  • N is a Save and N = A: N ∈ K.
  • N is a Save and N ≠ A: N was not acknowledged (its write failed, or the process stopped before the ack), so nothing after base(N) was acknowledged. Its writer had confirmed = base(N), so base(N) is A or a confirmed copy at least as new as A. If base(N) is still valid, it is in K. If it is not, some later write overwrote it. A writer only targets base(N)'s slot when K excludes it, which happens only when that writer had confirmed = N (first bullet). Then N was confirmed and is in K, and its payload is at least as new as A's.
  • N is a Recovery: it was never acknowledged, and if the Save after it had been confirmed, that Save would be newer than N. So A is covered by keep(N), the keep set of N's writer, by the same argument one step earlier. If a keep(N) generation is missing, a writer overwrote it. That requires N to have been confirmed: every write whose K excludes keep(N) runs with confirmed = N (the barrier's Save right after N), and later writes run only after that. Then N ∈ K, and its payload is the payload of the newest keep(N) generation.

Repeated failures stay safe. After a failed Recovery write, the next pass sees that Recovery as N, computes K = keep(N) again, and reuses the same target slot. This holds in one process and across restarts, because K depends only on the view, not on process memory. The argument assumes that a successful fdatasync after a full pwrite of the slot makes it durable. That is the T2d question (B1). The safety argument is a design claim until T3e, including its bounded exhaustive check, passes.

6.1.4 Crash-Safe Migration from raft_state.json#

The earlier draft wrote slot A directly into raft_state.slots and used the file's existence to skip JSON migration. A crash after the file is created but before slot A is valid would then suppress migration and find no valid generation. The revised rule is that raft_state.slots exists only if it already holds a valid generation.

The revision 1 rule "if migration fails with ENOSPC, stay on JSON for this run" was also unsafe. Once .slots may exist under its final name, any later JSON save can leave .slots stale, and the next start prefers .slots, which rolls back term and vote. Revision 2 defines migration as a state machine with one irreversible point, and fixes which backend may be written in each state.

Migration runs inside load_or_init (persistent.rs:115-190), before any RaftNode exists and before any other save. The other saves inside load_or_init (--reinit at :175, init at :380, remove_unknown_peer_metadata at :193-207) run after it and go through the backend it selected. A new node's initial save (today the init call at :134-140, which saves at :380) is not one of them: it is step F2 of "Fresh-node initialization" below, and it runs before migration, as the source of the migration. When load_or_init loads an existing .slots (state S on a restart), confirmed is unset (Section 6.1.3), so a normal save is not allowed yet. load_or_init therefore runs step 2 of the recovery barrier (Section 6.4.1) on the state file right after loading it and before any of those saves. If that fails, load_or_init returns an error and the process does not start. A later start is safe, because the keep set is computed only from the slots on disk. Right after a migration publish, generation 1 was confirmed by this process, so no barrier write is needed. A new node reaches S only through such a publish (Fresh-node initialization, below). When load_or_init ends in state J (migration skipped or failed), it runs the JSON variant of barrier step 2 instead, the startup rewrite in Section 6.1.5, under the same rule: before any other save, and if it fails, load_or_init returns an error.

Fresh-node initialization (state F). Revision 9 initialized a new node directly in the slot format. 6.1.5 JSON Backend When Migration Is Skipped (State J)#

A best_effort node stays in J when the precheck fails, when steps 3-4 fail (for example fallocate returns EOPNOTSUPP on a filesystem that is not on the allowlist), or when step 5 returns an error. This applies to new nodes as well: a new node first publishes its initial state as JSON and then migrates (Section 6.1.4, "Fresh-node initialization"), so on a filesystem without fallocate it starts in J instead of failing to start. Revision 5 said it "continues on JSON through AtomicFile" but its recovery barrier (Section 6.4.1, step 2) only knew how to write slots, so the JSON path had no defined recovery. This section defines it. A node in J has no reserved state file: every save needs new data blocks and a new inode, so on a full disk its first state save fails and it goes to R3. J is reported as degraded and in consensus_state_backend. The guarantee in Section 1 does not hold for it. It only keeps the same safety as S: no message after a save that is not durable, and no rollback past an acknowledged state.

AtomicFile is not used as a black box in J, because its sync behavior is not verified here (Section 6.1.4, step 1), and because one Err from it does not tell whether the rename happened. In every mode other than off, a JSON save is this explicit sequence. Each step runs only after the previous one returned success:

  1. 1.
    Create raft_state.json.tmp (truncating any leftover), write the serialized state, fdatasync it.
  2. 2.
    rename(raft_state.json.tmp, raft_state.json).
  3. 3.
    fsync the storage directory.

Persistent keeps json_confirmed, a digest of the payload whose save last completed all three steps in this process. Mutate-after-save (Section 6.1.3) applies unchanged. Failures fall into two classes:

Barrier step 2, Json arm, after a rebuild (Section 6.4.1): if the JSON latch is set, the pass fails. Startup rewrite (Json arm at process start). A new process cannot know how the JSON file it sees was written. It may come from an off run, an older binary or today's CBOR-to-JSON migration (all through AtomicFile), and a save in that run may have failed in a way that left page-cache-only bytes visible. So load_or_init in J, after the restart rules (which start with the storage-directory fsync, Section 6.1.4), loads raft_state.json and saves the same payload again through steps 1-3 before any other save. On success, json_confirmed is set and barrier step 2 counts as done for this start, as in Section 6.4.1. On a new node, the F2 save of this same start (Section 6.1.4) already wrote the loaded payload through steps 1-3 in this process, so it is this rewrite and no second one runs. On any failure, load_or_init returns an error and the process does not start (Section 6.6). Why the rewrite is safe: it never changes bytes in place. A crash before step 3 returns leaves the old file or a fully written copy of the same payload under the name. If the old file's bytes were only in the page cache, the crash exposes them as unparsable JSON, which refuses to start as it does today (load_json(..)? in load_or_init, persistent.rs:124-126). That is not a rollback, and no message was sent from them. After a successful rewrite the loaded state is durable, under the same assumptions as the slot protocol: a successful fdatasync of the new file (T2d) and a successful directory fsync after the rename (B1, T2c).

What the JSON arm still depends on. Like .slots, the safety of J after an unknown rename depends on B1. After a restart, a later successful directory fsync has to make the earlier rename durable, or at least keep the final name from going back to a file older than one renamed after it. Until T2c passes, this is a design assumption.

Leaving J. Migration is retried only at the next process start (restart rule "JSON, no .slots.tmp"). There is no in-process J → S transition after load_or_init returns.

6.2 Reserve Accounting#

  • Blocks that are already allocated are not "available" in statvfs terms. The collection disk guard and the quota manager both read available bytes (dev disk_usage_watcher.rs:49-72 through shard::quota::global().available_bytes; eabee371 through fs4::available_space, :102-125). So once the reserve is materialized, the free space they see drops by about its size (the exact amount includes filesystem metadata and is not something we control). Nothing is double-counted, and no special-casing is needed in the watcher.
  • Ordinary writers cannot use the reserve, because the blocks belong to files only Qdrant's consensus code writes. This is why a reserve that is released (a balloon file) is rejected: once freed, its blocks go to whichever writer allocates first.
  • Consensus writes never consult DiskUsageWatcher. Reserve capacity is tracked internally: materialized spare segments, plus remaining space in the open segment if it is materialized, plus slot size. Whether a given batch fits is decided by the exact placement check in Section 6.5, not by a byte total, because entries are never split across segments. Unreserved segments (failed backfill, or created by the best_effort fallback), closed-* segments, recycle-* files and files in the durability unknown state (Section 6.1.2) count as zero. In enforce, consensus WAL writes are limited to reserve capacity. In best_effort, a batch can also be placed in unreserved space, which comes from ordinary free space through the guard in Section 6.5. That space is reported separately and never counted as reserve.
  • The reserve does not help the collection guard. While ordinary free space is below 2 × wal_capacity_mb, every collection write, and therefore every meta-operation that writes a collection, keeps failing. R2 is what keeps Raft alive in that state.
  • Operators lose reserve_bytes of visible capacity per node. Startup logs and telemetry must report it.

6.3.1 Holding Both Apply Cursors#

There are two cursors, and both must stop at the failed entry:

  • Qdrant's apply queue (Persistent::apply_progress_queue, persisted). apply_entries_impl reads entries from the WAL by this queue's index (consensus_manager.rs:417-428), not from the Ready. So Qdrant does not depend on raft-rs redelivering entries.
  • raft-rs's applied index (raft_log.applied). It is set only by commit_apply (raft.rs:960-1004). The separate delivery cursor commit_since_index (raw_node.rs:302) advances when entries are handed out (:468-469) and never moves back, so raft-rs does not redeliver entries it already handed out in the same RawNode.

raft-rs reads the applied index in places that matter here: has_pending_conf (raft.rs:2788-2791) blocks new conf-change proposals while pending_conf_index > applied; the pre-campaign check scans (applied, committed] for unapplied conf changes and refuses to campaign if it finds one (raft.rs:1548-1567, :1583-1612); commit_apply runs the joint-consensus auto-leave hook when applied crosses pending_conf_index (raft.rs:984-1002). If a paused apply returned ordinary Ok, today's code would call advance/advance_apply (src/consensus.rs:1144, 1187) and move raft-rs's applied index past an entry Qdrant has not applied. That would let a leader accept a second conf change while the first is unapplied locally, and would fire auto-leave early. A paused apply must not reach advance or advance_apply.

The design uses raft-rs's documented split between append and apply. advance "advances the ready after fully processing it", and advance_append "advances the ready without applying committed entries. advance_apply or advance_apply_to should be used later to update applying progress" (raw_node.rs:654-680). advance_apply_to(applied) accepts any index in [prev_applied, committed] (raft_log.rs:322-339; it calls fatal! outside that range).

Proposed changes in src/consensus.rs:

  1. 1.
    apply_entries returns a typed outcome instead of anyhow::Result<bool>, for example ApplyOutcome { stop_consensus, paused: Option<PauseReason> }, marked #[must_use]. There is no "success" value that hides a pause.
  2. 2.
    process_ready replaces self.node.advance(ready) (:1144) with self.node.advance_append(ready), then self.node.advance_apply_to(store.last_applied_entry().unwrap_or_default()).
  3. 3.
    process_light_ready replaces self.node.advance_apply() (:1187) with the same advance_apply_to(last_applied_entry).
  4. 4.
    In the non-paused case, last_applied_entry equals the last delivered index (each delivered entry, including empty and user-error entries, calls entry_applied; snapshot install sets the queue to the snapshot index, entry_queue.rs:41-43), so behavior is unchanged. In the paused case raft-rs's applied index stays at the last entry that really applied. The value is monotonic because both cursors only move forward.
  5. 5.
    While paused, a timer in the consensus loop retries apply_entries with backoff even when no new entries arrive, then calls advance_apply_to(last_applied_entry). raft-rs allows advance_apply_to between readies; ready()'s restriction is on calling step, propose or campaign between ready() and advance (raw_node.rs:478-486). commit_apply can append an auto-leave entry (raft.rs:991-999); the next Ready carries it as usual.
  6. 6.

What this cannot prove from source alone is B3: that no other part of raft-rs, or of Qdrant (for example /readyz and the commit-based checks around src/consensus.rs:889), assumes applied catches up with commit_since_index within a bounded time. The prototype must run a cluster with apply paused for longer than the election timeout and a conf change in flight (T5c).

6.3.3 Partial Effects and the Shadow State Machine#

A capacity error can happen after a handler has persisted part of an operation. The comment at consensus_manager.rs:390-398 says so, and the current code reacts by invalidating the shadow state machine on every Err (:398). A pause must not bypass that.

Rules:

  1. 1.
    Shadow. On every capacity pause, call invalidate_shadow() exactly as the Err path does, before the next retry. The shadow then reloads from the state the handler left (consensus_shadow/mod.rs:62-90). The shadow is disabled by default (ShadowMode::Disabled) but the consensus tests enable it in panic mode (src/settings.rs:710-722), so a missed invalidation would show up there as a divergence panic.
  2. 2.
    Partial effects are not assumed idempotent. Today's dev rebuild also retries the same entry in the same process with the same TableOfContent, so it has the same exposure. This design does not claim that retry is safe; it limits pause to operations whose handlers are shown to be retry-safe after a partial failure. Retry-safe means: applying the operation again, after any prefix of its effects was persisted, gives the same final state as applying it once. Each ConsensusOperations and CollectionMetaOperations variant needs that audit (B2). Unaudited variants keep today's stop-and-rebuild behavior. For a variant that is not retry-safe, the handler must either be made retry-safe (for example by checking for and completing a partial result) or its capacity error stays fatal.
  3. 3.
    Reload before retry. For audited variants whose partial effects live in memory (for example collection config held by the TableOfContent), the audit must say what is reloaded from disk before the retry. If that cannot be done without a process restart, the variant is not pause-eligible.
  4. 4.
    Proposer waiters. apply_normal_entry removes the waiter and sends it the handler result before returning (consensus_manager.rs:638, :646-654). Today that means a proposer can get an error for an entry that a later retry applies. Under pause, a capacity error must not be sent: the waiter is re-registered (or not removed) and receives only the final result, or times out. A timeout must be reported to the client as "outcome unknown, operation committed", never as a failure.

6.3.4 Behavior While Paused#

  • Raft keeps appending, saving hard state, sending persisted messages and granting votes. Log replication continues, which is the point of the reserve.
  • The paused node's last_applied_entry and raft-rs applied index do not move. The log grows into the reserve.

  • Availability limits that follow from holding the applied index (from the raft-rs code above):

    • A paused leader ignores new conf-change proposals while has_pending_conf() holds; raft-rs replaces them with empty normal entries (raft.rs:2102-2131). Peer add/remove waits until apply resumes.
    • A paused node with an unapplied conf change in (applied, committed] refuses to campaign (raft.rs:1548-1567). If a majority of voters is paused behind a conf change, no new leader can be elected until one of them resumes. That is a liveness limit, not a safety violation.
    • Proposals that wait for apply on the paused node time out.
  • Readiness and /cluster report apply_paused: capacity with the stuck index and the backlog length.

6.4 R3: Behavior When the Reserve Is Exhausted#

  • Before a WAL append or state save, check the capacity. For the WAL this is the mode-aware placement check in Section 6.5. It runs before any conflict truncation of the batch, on the layout that truncation will leave (Section 6.5, "Preflight"), so a capacity rejection never follows a truncation, and a truncation error is handled as an append error (next bullets), never as a capacity rejection. In enforce, a batch that needs any unreserved placement returns ReserveExhausted. In best_effort, such a batch runs the unreserved-append guard, and a guard failure returns CapacityExhausted. Both errors are returned without changing the in-memory WAL index or Persistent, and every rule in this section applies to both. An entry whose footprint exceeds U is rejected the same way in both modes. State saves need no mode split: a .slots file is always materialized (Section 6.1.4), and the Json backend has its own failure classes (Section 6.1.5).
  • process_ready propagates the error. Persisted messages are not sent, because the ? exits before src/consensus.rs:1129.
  • The rebuild path reloads Persistent and ConsensusOpWal from disk before constructing a new RaftNode. This also fixes the stale-tail issue from Section 4. Any error from Wal::append triggers this reload, not only ReserveExhausted: a failed retire rename can return after retire_open_segment has already swapped the open segment in memory (wal/lib.rs:267-289), so the in-memory WAL cannot be trusted after an append error.
  • On the Json state backend (state J, Section 6.1.5) a state save error is handled the same way, with the clean/unknown classes and the JSON latch defined there.
  • Any fsync, fdatasync, msync or rename error on a reserved file is fatal for that file handle. Close it, then reopen and re-read it from disk. Never retry a flush on the same mapping and treat a later success as proof of durability. Reopening does not establish durability either (Section 6.4.1): the reloaded state is only a candidate until the recovery barrier passes.
  • The node then behaves like a crashed follower: it does not vote. It rejoins when space returns, once the barrier passes and the next batch is admitted: in enforce after the reserve is refilled, in best_effort as soon as the guard finds space. This is the current safe behavior, but it happens later, after the reserve is used up rather than as soon as the disk fills.
  • The reserve is refilled only from real free space, in the background, once the collection guard reports free space again.

6.4.1 Recovery Barrier After a Flush Error#

Problem. After msync or fdatasync fails, the process cannot tell which of the dirty bytes reached disk. Closing and reopening the file does not help: the reopened file is served from the same page cache, which can still hold the bytes whose writeback failed. Depending on the filesystem, those pages can even be marked clean after the error, so a later fdatasync on the new handle can return success without writing them. The same holds after a process restart without a reboot, because the page cache outlives the process. If Raft were rebuilt from such bytes and the node then voted or acked, it could treat an unsynced entry, term or vote as durable. A crash would then lose state the cluster relies on.

The fsync man page quoted in Section 5.2 does not describe what happens to the page cache after a writeback error. This section therefore assumes the worst case above and does not rely on any filesystem-specific error reporting.

Rule. A rebuilt or restarted node in any mode other than off does not create a RaftNode, and therefore sends no messages at all (no votes, no append acks, no leader appends, no heartbeats), until one complete pass of the barrier below has succeeded. Proposals and reads that need the consensus thread fail as they do today while consensus is down.

Barrier steps, run on fresh handles after the reload from Section 6.4, each step only after the previous one returned success:

  1. 1.
    Rewrite the recovered WAL bytes. For every segment in the recovered log (open-* and closed-*), pwrite the bytes of its valid range, as parsed by Segment::open (header plus the CRC-valid entries), back to the same offsets, and, during a rebuild where the old in-memory size() is still known and larger, pwrite zeros from the end of the valid entries up to it. (At startup that size is unknown. Stale entries beyond the valid range can then come back after a crash, which is the "prefix of the old log" case already accepted in Section 6.1.2.1.) Then fdatasync the file. Writing the bytes again marks the pages dirty, so the following fdatasync has to write them whether or not the earlier writeback error left them clean. On a reserved segment the rewrite overwrites materialized ranges, so it allocates nothing new (subject to B1, like every other write). On an unreserved segment (best_effort, Section 6.5), the rewrite uses pwrite, never a store through a mapping. Rewriting entry bytes whose writeback failed, or zeros over holes beyond them, may need new blocks. On a disk that is still full, the pwrite or fdatasync returns an error, so the pass fails and the node stays fail-closed (see "Failure") until space returns. It never sends a message based on those bytes.
  2. 2.

    Make the recovered Raft state durable. This step depends on the state backend (Section 6.1.4) and matches it exhaustively:

    • Json (state J): the rebuild check or the startup rewrite in Section 6.1.5. Neither writes in place, and both fail while the JSON latch is set. The sub-steps below do not apply.
    • Slots (state S): publish the recovered state as a new generation, without touching any kept slot, as follows.

    Revision 4 rewrote the newest slot in place. That could destroy an acknowledged generation and fall back to an older one (Section 6.1.3), so it is removed. Instead, on a fresh read of all three slots (Section 6.1.3):

    1. 1.
      Compute the keep set K from the view, with confirmed unset, and let N be the newest valid generation. Raft is rebuilt from N's payload.
    2. 2.
      Recovery write. Write generation N + 1, kind Recovery, keep = K, with N's payload, into the target slot outside K, then fdatasync. No slot in K is written, so if this write tears, or its fdatasync fails, or the process crashes, every generation that may have been acknowledged is still intact on disk. Once the fdatasync succeeds, confirmed = N + 1.
    3. 3.
      Confirming save. With K = {N + 1}, run a normal save (Section 6.1.3) of the same payload: generation N + 2, kind Save, base = N + 1, into the lowest slot other than N + 1's, then fdatasync. Step 2 passes only when this fdatasync succeeds. This save is what lets a later keep-set computation drop an unconfirmed Recovery slot. Without it, a Recovery slot that was followed by acknowledgments would look the same as one whose write failed, and the next pass would have to keep three generations.

    At process start, load_or_init has already run this step before its own saves (Section 6.1.4). The startup barrier treats step 2 as done if, for Slots, confirmed is still equal to the newest valid generation, or, for Json, json_confirmed is set and the JSON latch is not, that is, if no state save error has happened since.

  3. 3.
    Directory metadata. fsync the WAL directory and the storage directory. Files marked durability unknown and the detach latch keep their in-process meaning (Section 6.1.2): a successful directory fsync here does not clear them.
  4. 3a.
    Snapshot reconciliation. This is the check that ConsensusManager::new runs today (consensus_manager.rs:127-146): if hard_state.commit == latest_snapshot_meta.index (the last state change was a snapshot install, whose update_from_snapshot sets both in one save, persistent.rs:68-109) and the WAL's last entry has index < snapshot index, the WAL still holds pre-snapshot entries that apply_snapshot did not clear before a crash or error (consensus_manager.rs:791), and it is cleared now. In modes other than off, this check moves into the barrier and runs at startup and on every rebuild, after steps 1-3. Two reasons for that order: the decision reads the recovered state, which must be durable first (step 2), or a crash could leave the pre-snapshot state on disk with its entries already cleared; and a rebuild after a failed wal.clear() inside apply_snapshot reaches the same state without going through ConsensusManager::new. The clear is Wal::truncate(first_index), branch B (or A, Section 6.1.2.1), done with the durable algorithm. Unlike today's let Ok(Some(last)), an error from reading the last entry, or from the clear, fails the pass (see "Failure"). It does not silently skip the check. The barrier first checks the latch and the conditions of the clear, so a latched WAL fails the pass instead of entering a structural truncation. In off mode the check stays in ConsensusManager::new, unchanged.
  5. 4.

    Validate the recovered state against the recovered log, after step 3a. The indices are the ones raft-rs will see through the Storage implementation (consensus_manager.rs:1389-1402), so the check accepts exactly the states that the rebuilt RaftNode can start from:

    • snap = latest_snapshot_meta.index (0 if no snapshot was ever installed); applied = last_applied_entry(), or 0 if None; commit = hard_state.commit;
    • WAL non-empty: first and last are the Raft indices of its first and last physical entries. Right after a reload, compacted_until_raft_index is 0 (consensus_wal.rs:38-44), so first_entry/last_entry return physical entries;
    • WAL empty: first = snap + 1, last = snap.

    Invariants:

    • commit ≤ last;
    • applied ≤ commit (the commit index is saved before committed entries are applied, src/consensus.rs:1110 before :1136, and :1173 before :1183, and mutate-after-save keeps that order on disk);
    • first ≤ applied + 1, so every entry in (applied, commit] is still in the log (compaction stops at last_applied and always keeps one entry, consensus_manager.rs:1109-1136, consensus_wal.rs:291-296; compact_wal already debug_assert!s this);
    • if the unapplied queue [cur, q_last] is non-empty, it lies within [first, last];
    • every recovered entry has entry.index == wal_to_raft(wal_index), checked explicitly (not through debug_assert!, Section 6.1.2.1).

    Pass. Only now may RaftNode be constructed from the recovered state (the existing rebuild in src/consensus.rs:149-222) and messages be sent.

Failure. If any pwrite, fdatasync or directory fsync in steps 1-3 fails, if the Json arm of step 2 fails (including while the JSON latch is set), or if step 3a fails (an error from reading the last WAL entry, or from the durable clear), the pass fails. The node stays fail-closed: no RaftNode, no messages. It closes the handles, waits with the existing consensus backoff (src/consensus.rs:48-55), reloads from disk and runs the whole barrier again from step 1. A failed step is never retried on the same handle, and no partial pass counts. A failed step 2 write is not retried in place either: the next pass recomputes K from a fresh read. An unconfirmed Recovery slot is outside K, so it is the next target. Repeated failures, in one process or across restarts, therefore keep reusing one slot and never reach a kept one (Section 6.1.3). If step 4 fails, the recovered state is inconsistent, and retrying cannot fix that. The node stays fail-closed, reports consensus_recovery_blocked with the violated invariant, and needs operator action (for example a restart after the disk is repaired, or --reinit). It never repairs the invariant by moving commit or applied, because either could hide a lost entry.

When the barrier runs.

  • After every rebuild that follows a WAL append error (including a flush error on an unreserved segment, Section 6.5), a truncate_durable error, a state save error (slot or JSON), ReserveExhausted or CapacityExhausted (Section 6.4).
  • At every process start in modes other than off, before the first RaftNode is created (src/consensus.rs:367-385), because a restart without a reboot sees the same page cache. This also covers the case where the previous process failed in the middle of a barrier.

What the barrier does not prove. It relies on two properties that no cited source states: that a pwrite of the same bytes makes the pages dirty again after an earlier writeback error, and that a subsequent successful fdatasync on a new handle then means those bytes are on disk. Both are part of B1 and are tested by T2d. The slot rule in Section 6.1.3 depends on the second property for every confirmed generation. The Json arm (Section 6.1.5) depends on it for the new file of each save and of the startup rewrite, and also on B1/T2c for renames. Until T2d passes on a filesystem, the barrier is a design assumption there, not a verified property.

Cost. Step 2 writes two slots (2 × S_slot bytes) and two fdatasyncs on Slots. On Json it is a re-read after a rebuild, and one file write plus fdatasync, rename and directory fsync at startup. Step 1 rewrites the used part of every retained segment. With the defaults (retain_closed 1, segments of 32 MiB) that is at most a few segments, but a long apply pause keeps more segments in the log (Section 6.5). The cost must be measured at startup and after an error (Section 9, risk 14).

6.5 Sizing Method (No Assumed Constants)#

Inputs. Only E_cap is a hard limit. The others are measured per deployment or chosen as product decisions:

  • E_cap: hard cap on the encoded size of one consensus WAL record (ConsensusOperations + raft framing). Configured (reserve.max_entry_bytes in the consensus section, Section 6.6), the same on all nodes like C, and enforced at proposal time (below). It must satisfy footprint(E_cap) ≤ U. This is the only entry-size input to the guaranteed bound.
  • E_obs: largest encoded entry seen so far (telemetry). A statistic, used to choose E_cap, never used in the bound.
  • F_avg: average on-disk footprint per entry, measured as the mean of footprint(len) over real entries (not footprint of the mean length, because padding makes footprint non-linear). A statistic, used only for the nominal estimate below, never in the bound.
  • R: committed entries per second while the disk is full (including peer metadata and transfer churn)
  • T: the ride-through time we target (product decision)
  • C: configured segment capacity (32 MiB default, wal/lib.rs:37-41)
  • S: largest serialized Persistent (grows with peers, metadata and cluster metadata)

Segment layout, from source:

  • On-disk footprint of one entry of len bytes: footprint(len) = 8 (length) + len + padding(len) + 4 (CRC) (segment.rs:22-26, 345-370), where padding(len) = (4 - len) mod 8 (:691-693). So footprint(len) is a multiple of 8 and at most len + 19.
  • Segment::create rounds the capacity down to a multiple of 8 (:144), and the 8-byte segment header uses the start of the file. Usable bytes per segment: U = (C & !7) - 8.
  • Wal::append never splits an entry across segments. If the entry does not fit in the remaining space of the open segment, it retires that segment and puts the entry in the next one (wal/lib.rs:294-308, sufficient_capacity at segment.rs:556-560). The unused remainder of the retired segment is lost to packing.

Why ceil(L / C) is wrong. It assumes bytes pack perfectly. With entries whose footprint is just over U / 2, every segment holds exactly one entry, so N entries need N segments, about twice ceil(L / C). Revision 3 used that formula; it is replaced.

Worst-case segment bound. Let F_max = footprint(E_cap) and k = floor(U / F_max), so k ≥ 1. Consider N entries, each with footprint ≤ F_max, appended after the current open segment. Every segment that is retired while receiving them was retired because the next entry did not fit, so it holds more than U - F_max bytes of the new entries. Since each entry is at most F_max, it holds more than U / F_max - 1 of them, so at least k. The current open segment is counted as holding none of them, which is conservative. Then the number of new segments needed is at most

S_log_max(N) = 1 + floor(N / k)

For entries just over U / 2, k = 1 and the bound is 1 + N. The bound holds for any order of entry sizes and does not depend on the mean entry size or on measured packing efficiency.

Why there is no byte term. Revision 4 used 1 + min(floor(L / (U - F_max + 1)), floor(N / k)) with L = N × F_avg. F_avg is a mean observed in the past, not an upper bound on the bytes of the next N entries, so the min could pick a value below what the backlog really needs. Example: history has F_avg = 200 bytes, C = 32 MiB, and the backlog during the pause consists of entries just over U / 2. The byte term is then floor(200 N / (U - F_max + 1)), which is 0 for any N below about 84,000, so revision 4 sized for 1 new segment while the backlog needs N. That formula was not a worst-case bound, and it is removed. A byte term is valid only with a guaranteed byte bound L_max = N × F_max. With that, it is never smaller than the count term: k × F_max = U - (U mod F_max) ≥ U - F_max + 1, so N / k ≤ N × F_max / (U - F_max + 1). The min would always select floor(N / k), so the bound uses only that term.

Nominal estimate (not a bound). For planning and dashboards, telemetry may also report S_log_nominal(N) = 1 + ceil(N × F_avg / (U - F_max + 1)), labeled as an estimate. It assumes the backlog looks like history and can be far below the real need. It is never used for reserve.segments in enforce, for alert thresholds, or in admission. A large gap between S_log_nominal and S_log_max shows how much a tighter E_cap would save.

Formulas (worst case for the chosen N):

  • Backlog during a pause: N = ceil(R × T) entries. N is an entry count, and rounding up keeps the planning target conservative for any non-integer R × T.
  • reserve_segments = S_log_max(N) + 1 (open) + retain_closed (1) + P (spare) + 1 (recycle in flight)
  • reserve_bytes = reserve_segments × C + 3 × S_slot (three state slots, Section 6.1.3), with S_slot ≥ 2 × S_observed for growth headroom.

These formulas size the reserve at planning time. R and S are measured inputs, and E_cap is chosen from the measured distribution (E_obs); the document does not assume values for any of them. Telemetry for the footprint distribution, R and S should ship first, before the defaults are chosen. What the bound is conditional on. S_log_max(N) is a worst-case bound only for the chosen N and only if every one of those N entries has footprint ≤ F_max, that is, is within E_cap. R and T are measured and planning inputs. Nothing enforces them. If the real backlog has more than N entries, or contains over-cap entries (see "E_cap enforcement" below), the reserve can run out before T, and the node goes to R3. That shortens the ride-through, which is an availability limit. It is not a safety limit, because runtime admission places each entry by its real footprint and never relies on N, R, T or E_cap.

E_cap enforcement, and safety when it is exceeded.

  • Proposal time. Before propose (and propose_conf_change), the node computes the encoded size of the record, including the largest raft framing for the entry type. If it exceeds E_cap, the proposal is rejected with a client error before anything enters the log. Entries that raft-rs creates itself (the empty entry after an election, the auto-leave conf change) do not go through this path. The configuration therefore sets a minimum for E_cap that is above their size, and T11b checks that bound.
  • Exceeded anyway. The cap is a sizing assumption, not a safety mechanism. An entry above E_cap can still reach a follower: from a leader with a different configuration, from an older binary in a mixed-version cluster, or from entries proposed before the cap existed that are still in the log at upgrade. Runtime admission (below) does not trust the cap. It places every entry by its real footprint, so an over-cap entry with footprint ≤ U is appended only if it fits in materialized, durably published space (enforce) or passes the unreserved-append guard (best_effort), and an entry above U is rejected as before in both modes. An over-cap entry therefore cannot cause an unsafe append. It can only make the ride-through shorter than planned. Followers do not reject over-cap entries: that would turn a configuration mismatch into R3 on every follower. Over-cap entries are counted in consensus_entries_over_cap_total, which is an alert, because the guaranteed bound no longer holds for that backlog.

Runtime admission (R3), exact, not estimated, and mode-aware. Revision 6 started the simulation with r = 0 for an unmaterialized open segment and counted only materialized spares, in every mode. A best_effort node with no reserve (a filesystem without fallocate, or a failed backfill) then rejected every nonempty append, even with ordinary free space available. That contradicted the best_effort rows of Section 6.1.1. Revision 7 simulates over the real segment sequence and tags each placement, and the mode decides what an unreserved placement means. Revision 7 still started that simulation from the open segment as it was before append_entries truncated a conflicting suffix (consensus_wal.rs:213). In enforce it could then reject a replacement that fits once the suffix is gone (a full open segment, no spare, and a conflict inside the open segment). In best_effort the guard could allocate ranges, or create segments, that the real append never writes, while leaving unguarded the ranges it does write. Revision 8 starts the simulation from the layout the truncation will leave, computed without mutating anything.

Preflight. Today append_entries checks, truncates and appends entry by entry (consensus_wal.rs:171-256), so a check that fails on a later entry returns after earlier entries were appended, and a truncation can in principle happen in the middle of a batch. In modes other than off, every check moves into a preflight that covers the whole batch and runs before any mutation:

  1. 1.
    Encode. Encode every entry once and record its length len_j. The same buffers are used for the appends, so the lengths the simulation uses are the lengths that are written.
  2. 2.
    Validate, with the same checks and errors as today's loop (logical compaction :173, None from try_raft_to_wal :185-190, gap :197), plus contiguity: e[j].index = e[0].index + j for every j. raft-rs hands out the entries of a Ready as one contiguous run; this is not line-checked here, and T11c records it. Under contiguity only the first entry can conflict: each later entry's WAL index is exactly one above its predecessor's. A batch that fails any check returns Err before any mutation. For a non-contiguous batch that is a change from today, which would truncate in the middle of the batch; failing closed is chosen over admitting a layout the preflight did not simulate.
  3. 3.
    Plan the truncation. If the WAL is non-empty and w_0 = try_raft_to_wal(e[0].index) is below last_index + 1, the truncation point is from = w_0, and the plan is Wal::truncate_plan(from) (Section 6.1.2.1). Otherwise there is no truncation.
  4. 4.
    Refuse what cannot run. Plan D: return Err (see below). Plan B or C while the detach latch is set (Section 6.1.2): return Err, because Wal::truncate would refuse anyway, and refusing here keeps the guard from doing work for a batch that cannot be appended.

The preflight input is therefore exactly (plan, [len_0, ..., len_{m-1}]), where plan is none, A(k), B(i), C(i, kept) or D.

Branch D in append_entries. Plan D means w_0 < first_index: the leader sends an entry below the first physical entry, which Qdrant removed only after applying it, so the entry is committed. Today's loop would also misplace the rest of such a batch: after branch D the WAL index restarts at 0, but current_index_offset is the one computed before the truncation (:166), so the second entry fails the gap check after the first was appended. No call path is shown to reach it (Section 6.1.2.1), so the preflight rejects it with Err before mutation, which leads to today's stop-and-rebuild, and T4g records whether any input reaches it.

Simulation. The WAL simulates the placement of the whole batch with the same rule as Wal::append, over the sequence of segments the batch would use, starting from the post-truncation layout: the open segment with the o and r from the table in Section 6.1.2.1 (with no plan: o is the current end of the open segment and r its remaining usable bytes), whatever its class; then the spares in the creator's pending list, in the order the creator hands them out; then segments the creator would still have to create. Spares that are not yet durably published (gate G2, Section 6.1.2) are not in the pending list, and neither are segments the batch's own truncation detaches. For each entry in order:

  1. 1.
    If footprint(len) > U, reject the batch in both modes: no segment could hold it without ensure_capacity growth (Section 6.1.1).
  2. 2.
    Else if footprint(len) ≤ r, place it in the current segment at byte offset o, then set o += footprint(len) and r -= footprint(len).
  3. 3.
    Else move to the next segment in the sequence, place it there at offset 8, and set o = 8 + footprint(len) and r = U - footprint(len). If the detach latch is set, return Err instead: the retire rename would be refused (Section 6.1.2), and refusing here keeps the rejection before mutation.

Every placement is the triple (segment, offset, footprint), so the simulation yields the exact byte ranges the appends will write. Each placement is reserved if its segment is reserved (Section 6.1.1: materialized and durably published), and unreserved otherwise, including every placement in a segment that does not exist yet. The batch is then decided by mode:

  • enforce: if any placement is unreserved, return ReserveExhausted, even if ordinary free space exists. An enforce node always has a reserved open segment and only reserved spares: it refuses to start otherwise (Section 6.1.1), and its creator never makes an unreserved segment. So this is exactly revision 6's rule, with r taken after the batch's truncation: r from the materialized open segment, s durably published materialized spares, and ReserveExhausted when an entry needs a new segment and s = 0.
  • best_effort: reserved placements are admitted as in enforce. If there are unreserved placements, the batch runs the unreserved-append guard below, and is rejected only if the guard fails. A node with zero reserve therefore keeps appending while ordinary free space exists. Reserved space is used first only where it comes first in the segment order. A sparse open segment is filled before a materialized spare, as Wal::append does.

This is where the partial capacity of the open segment is counted: exactly, entry by entry, not as a byte total, and after the batch's own truncation. Bytes that a branch A truncation frees in the open segment are credited, because the batch writes into them. Segments in recycle-*, retired segments, segments the truncation detaches and the tail freed inside a branch C boundary segment are never counted (Section 6.1.2.1).

Order of execution. Each step starts only after the previous one returned success:

  1. 1.
    Preflight and mode decision (above). Any rejection (ReserveExhausted, a check error, plan D, the latch) returns before any mutation. The conflicting suffix is still on disk and in memory. That is a state Raft accepts: it is the same as the leader's append not having arrived yet.
  2. 2.
    Guard (best_effort, only if there are unreserved placements; below). It runs before the truncation. None of its effects changes a byte the log can read: fallocate mode 0 over a range inside the file leaves existing data as it is, including entries the truncation is about to remove, and a segment it creates only joins the pending list. A guard failure returns CapacityExhausted before any mutation, with the old suffix intact.
  3. 3.
    Truncation, if planned: the durable algorithm of Section 6.1.2.1, executing the plan from the preflight. If it fails, append_entries returns Err with no append (G3). That error comes after a possible mutation, so it takes the append-error path: reload from disk and the recovery barrier (Sections 6.4, 6.4.1). Blocks the guard allocated stay inside their files and do not count as reserve; segments the guard created stay in the pending list (they passed G2). Both are used by the next attempt, which runs its own preflight against the reloaded WAL.
  4. 4.
    Appends. In Materialize mode each append first checks that it lands at the planned segment and offset. A mismatch is a bug in the simulation. It returns Err before the store, through the append-error path. On disk the log is then the "after step 4 (C) or step 3 (B, D)" or the branch A target state of Section 6.1.2.1, [first, from), and no message was sent.
  5. 5.
    Flush, then the persisted messages, as today.

The plan stays valid from step 1 to step 4. append_entries holds &mut to the WAL on the consensus thread, so nothing else appends, truncates or retires. The background creator only adds spares at the end of the pending list, and only Wal::append consumes them, so the sequence the simulation used is a prefix of the list until the batch's own retires take from its front. Recycle step 3 for segments that this batch detached also adds at the end, and the plan never uses them.

Unreserved-append guard (best_effort only). It runs after the preflight and before the truncation and the first append. Each step starts only after the previous one returned success:

  1. 1.
    Create missing segments now. If the batch needs segments beyond the pending list, create them synchronously through the creator, so that no segment is created in the middle of the batch. Creation tries Materialize first (Section 6.1.1). Only on EOPNOTSUPP does it fall back to today's ftruncate creation, which yields an unreserved segment. A new segment joins the pending list only after the creator's directory fsync succeeded (segment_creator.rs:53-54), the same condition as G2. ENOSPC from fallocate is not retried as a sparse segment (Pool, Section 6.1.1).
  2. 2.
    Allocate the unreserved ranges. For each unreserved placement in a segment that is not materialized (a sparse open segment, a sparse spare, or a segment just created sparse), call fallocate mode 0 over the byte range [offset, offset + footprint) of its placement from the simulation, rounded outward to the larger of the page size and f_bsize. After a conflict truncation these are post-truncation offsets: in branch A they start at the end of the kept entries, and in branches B and C at offset 8 of the open segment, inside bytes that still hold the entries being removed. If the plan truncates a segment that is not materialized, the guard also covers the range truncate_durable will zero there ([o, old end) in the open segment; in branch C, the removed tail of c[i]). Those bytes held entries whose flush succeeded, so the call normally allocates nothing; it keeps the zeroing stores out of holes. The range is inside the file, so the size does not change, and existing bytes stay as they are (the argument from the backfill steps in Section 6.1.1). After a successful call, the man page guarantees that later writes into the range do not fail for lack of space (Section 5.2), subject to unwritten-extent conversion (Section 5.3 row 2: the guard writes no zeros). The range still does not count as reserve. If fallocate returns EOPNOTSUPP, the segment is marked unguarded for the rest of the process (counted in consensus_reserve_unguarded_segments), and its stores use today's sparse semantics.
  3. 3.
    Reject on any other error. Any other error from steps 1 or 2 (ENOSPC, EIO, a failed create, rename or directory fsync) returns CapacityExhausted before any mutation, and before the truncation, so the conflicting suffix is untouched. R3 (Section 6.4) handles it exactly like ReserveExhausted. Blocks that step 2 already allocated for earlier entries of the batch stay with their segment. They are inside the file, read as zeros or still hold the entries a planned truncation would have removed, and are used by the next attempt.

The guard does not consult DiskUsageWatcher. "Ordinary free space" means whatever the syscalls above find.

Failures after the guard. The batch's stores into the mapping then run as today, followed by msync. A failure there cannot be rejected before mutation, because the in-memory index already moved (Section 4, step 3). Each case still keeps the Raft rule that no persisted message follows a write whose flush did not succeed:

  • Reported error. msync, or a retire rename, returns an error. This is the existing append-error path (Section 6.4): the handle is closed, Persistent and the WAL are reloaded from disk, and no message is sent until a recovery barrier pass succeeds (Section 6.4.1). On an unreserved segment, barrier step 1 may need new blocks. While the disk is still full, the pass fails, and the node stays fail-closed and retries with backoff. It recovers when space returns.
  • Process-terminating fault. A store into a hole that cannot be backed can raise a fault such as SIGBUS (Section 5.3; T2 records the actual behavior). This applies to unguarded segments, and possibly to guarded ranges whose unwritten-extent conversion needs metadata. Qdrant does not handle that signal: resuming after a failed store through a mapping is not something this design can specify safely, so the process terminates. That is a crash during an append. The batch was not flushed, so no persisted message for it was sent (Section 4, step 5). The next start runs the startup barrier before any RaftNode exists (Section 6.4.1), and the log is a CRC-valid prefix (Section 7). If the disk is still full, the next unguarded store can fault again, so the node can crash-loop, taking collection serving down with it. That is what today's code (off) does on the same filesystem. It is not a regression, and no guarantee covers it (Section 9, risk 18).
  • Silent loss. A store that the page cache accepts, whose writeback later fails while msync returns success. msync(2) does not document how writeback errors are reported (Section 5.2). Today's consensus WAL makes this assumption for every write, in every mode. The unguarded path inherits it and adds no new one. For holes on a full disk it is unverified, so T2f checks it on a disposable fault-injection device. If T2f finds silent loss, the fallback contract changes to fail-closed: step 2 treats EOPNOTSUPP as a guard failure and returns CapacityExhausted instead of marking the segment unguarded. A best_effort node on a filesystem without fallocate then rejects every append that needs an unreserved placement (Section 9, risk 18). Until T2f has run, the unguarded path is a design target.

The consensus_reserve_bytes_free metric reports r + s × U, counting only reserved space: r is 0 when the open segment is unreserved, and s counts reserved spares only. For alerting it also reports the worst-case number of entries that still fit, floor(r / F_max) + s × k, because the byte value overstates what a run of large entries can use. That number assumes every coming entry is within E_cap. Neither value is an admission input. Unreserved appends are counted separately in consensus_wal_unreserved_appends_total, labeled guard = fallocate | none, and guard rejections in consensus_wal_capacity_exhausted_total.

6.6 Configuration, Observability and Rollout#

Configuration (consensus section):

  • reserve.mode: off | best_effort | enforce

    • off: today's behavior.
    • best_effort: try to materialize, backfill and migrate; on failure, continue with the degraded behavior defined in Sections 6.1.1, 6.1.4 and 6.1.5 and report degraded. WAL admission uses the reserve where the batch lands in reserved segments, and places the rest in unreserved space through the guard in Section 6.5. A node with zero reserve therefore keeps appending while ordinary free space exists, rejects before mutation (CapacityExhausted) when the guard finds no space, and on a filesystem without fallocate behaves like off for WAL capacity (Section 6.5, "Failures after the guard"). A skipped or failed migration means the node runs on the Json state backend (Section 6.1.5): it has no reserved state file, so the R1 guarantee does not hold for it, but it keeps the same fail-closed rules and its own barrier step 2. Warn if the filesystem is not on the allowlist. Six failures refuse to start even here, because no safe degraded state exists: a backfill verification mismatch, a failed startup directory fsync (WAL directory, or storage directory before the restart rules), a failed directory fsync after the migration publish rename (state P?), a failed directory fsync after the legacy CBOR-to-JSON save (state C), a failed new-node JSON save or its directory fsync (state F, step F2, Section 6.1.4), and a failed startup state write in load_or_init (barrier step 2 on Slots, Section 6.1.4, or the JSON startup rewrite on Json, Section 6.1.5). The last one means that a best_effort node with too little free space for one temporary JSON file does not start. Today's code would start, and then fail its first state save.
    • enforce: refuse to start if materialization, backfill of the open segment or the P spares, or migration fails, or the filesystem is not on the allowlist. At runtime, WAL admission counts only reserved capacity and returns ReserveExhausted for any unreserved placement, even with ordinary free space available. The segment creator never makes an unreserved segment (Section 6.5).
  • reserve.segments, sized as in Section 6.5 from S_log_max, never from the nominal estimate.
  • reserve.max_entry_bytes (E_cap, Section 6.5): enforced at proposal time, must be the same on all nodes, with footprint(E_cap) ≤ U and a minimum above the size of entries raft-rs creates itself.
  • Optional consensus_storage_path for operators who want a dedicated volume. A dedicated volume isolates blocks, inodes, directory entries and metadata from collection writers, which is stronger than R1 and is the only answer if B1 fails. It needs Helm or operator changes and does not replace R2. R1 still applies on that volume.

Metrics: consensus_reserve_bytes_total, ..._free, consensus_reserve_mode (including degraded), consensus_apply_paused, consensus_unapplied_entries, consensus_reserve_recycle_fallback_total (recycle fell back to delete), consensus_reserve_unmaterialized_segments (backfill failed), consensus_reserve_durability_unknown_files, consensus_reserve_entries_free_worst_case (Section 6.5), consensus_entries_over_cap_total (Section 6.5), consensus_reserve_segments_nominal (estimate only, labeled as such), consensus_recovery_barrier_failures_total, consensus_recovery_blocked (Section 6.4.1), consensus_state_backend (json or slots, Section 6.1.5), consensus_state_json_latched (Section 6.1.5), consensus_wal_unreserved_appends_total{guard} and consensus_wal_capacity_exhausted_total (Section 6.5), consensus_reserve_unguarded_segments (Section 6.5), and filesystem type.

Alerts:

  • reserve free below 50% (paging);
  • apply paused for longer than N minutes;
  • reserve materialization or migration failed at startup, including any node with consensus_state_backend = json in best_effort;
  • recycle fallback count increasing;
  • any entry above E_cap appended (consensus_entries_over_cap_total increasing);
  • a best_effort node appending into unreserved space (consensus_wal_unreserved_appends_total increasing), labeled with guard = none when the node can crash on a full disk (Section 6.5).

Rollout:

  1. 1.
    Ship telemetry only.
  2. 2.
    best_effort off by default, then opt in on canary clusters. The first best_effort start runs backfill and migration while free space exists; check degraded, the unmaterialized-segment metric, consensus_state_backend, consensus_reserve_unguarded_segments and consensus_wal_unreserved_appends_total before going further. A node left on json has no state reserve and should be given free space and restarted, so that migration retries. A node with unreserved WAL segments has no WAL reserve for them. Neither node has the guarantee, which only enforce claims.
  3. 3.
    Default best_effort. This requires T2e and T2f to pass first. If T2f finds silent loss, the fail-closed fallback from Section 6.5 ships instead of the unguarded path. Then a best_effort node on a filesystem without fallocate cannot append past its reserved space at all, so making best_effort the default on such filesystems is reconsidered at that point.
  4. 4.
    Consider enforce only on filesystems that passed qualification (Section 5.4). Before switching a node, check that it is not degraded: enforce refuses to start otherwise, and, unlike best_effort, never appends into ordinary free space.

Rollback: the slot format is not readable by older versions. Keep the .migrated files and provide a downgrade tool (or --reinit guidance). The downgrade tool must write the current slot state back to raft_state.json, not restore either .migrated copy, which are stale. Its steps: (1) load .slots, refuse if no slot is valid; (2) write raft_state.json from the current slot through AtomicFile, then fsync the directory; (3) rename(raft_state.slots, raft_state.slots.downgraded), then fsync the directory. A crash between (2) and (3) is safe: the new binary uses .slots and ignores JSON, an older binary uses JSON, and both hold the same state (if the new binary starts first, its step 7 retry renames the JSON away again, and the tool must be re-run before downgrading). Step (3) is needed so that a later re-upgrade does not load the old .slots over JSON saves made by the older binary: after (3), the new binary sees "JSON, no .slots.tmp" and migrates again. The tool leaves raft_state.cbor.migrated and raft_state.json.migrated alone; older binaries read only raft_state.json and raft_state (persistent.rs:23-26, 122-129), so they ignore both. If step 7 of the migration never completed, a stale raft_state.json, and possibly a still older CBOR raft_state, are still present; an older binary started without the tool would load one of them and roll back term and vote, so starting an older binary on a migrated node without the tool is unsupported in every case. Older binaries ignore recycle-* files (wal/lib.rs:582), so they leak space but stay correct. Mixed-version clusters are unaffected, because the on-wire Raft protocol does not change.

9. Open Risks and Unknowns#

Open validation and implementation gates. These are not design-review objections (see "Review Decision" for the review status). They block implementation beyond a prototype and any rollout of a mode other than off until resolved:

  • B1. Metadata operations on a full filesystem. Hard blocker, not a proven property. rename(2) and fsync(2) document ENOSPC. Segment recycling still performs two renames and two directory fsyncs per segment, and retire performs one rename. Whether retire renames, recycle renames, directory syncs, inode updates or journal writes can fail on ext4/XFS when the reserve is materialized and ordinary free space is zero is not known. A second, related unknown: after a directory fsync fails following a successful rename, does a later successful directory fsync (in the same process, or after a restart without a crash) make that rename durable? Gates G1/G2 and the migration state P? make every such failure safe by design (no invalid file, no missing committed prefix, no stale entries, no JSON/slots rollback), at the cost of reserve or of refusing to start. They do not make these operations succeed, so on a full disk the reserve can shrink with each failed recycle until R3 triggers. Resolution: T2b (frequency of ENOSPC on each operation) and T2c (what a later directory fsync proves), and T4d for the safety of the gates. If renames or directory syncs can fail on a full disk, either move these operations off the hot path (a fixed-name ring format for the consensus WAL, which is a larger change to lib/wal), or require a dedicated volume for the guarantee. If T2c shows a later fsync proves nothing, startup recovery must treat every recycle-* and empty open-* as unusable until a crash-consistent check exists, which further limits reuse. A third unknown, for file data rather than names: after msync/fdatasync fails, does rewriting the same bytes and a successful fdatasync on a new handle make them durable? The recovery barrier (Section 6.4.1) depends on it. Resolution: T2d. If it fails on a filesystem, the barrier cannot establish durability there, and that filesystem cannot be on the enforce allowlist.
  • B2. Retry safety after partial effects. No source shows that every consensus operation handler is idempotent after a partial failure. Resolution: per-variant audit plus T5f. Only audited variants are pause-eligible.
  • B3. Long-held applied index in raft-rs. Source reading (Section 6.3.1) shows raft-rs supports advance_append + advance_apply_to, and identifies the conf-change and campaign checks that read applied. It does not prove there is no other assumption about bounded apply lag. Resolution: T5b and T5c.

Other risks:

  1. 1.
    Startup panics are outside this design. Shard load panics while flushing segment state or ID-tracker mappings kept ...-36 down. Without a separate change (load failure marks the shard dead instead of panicking the process), R1–R3 do not help that node.
  2. 2.
    Quorum impact is unproven. Two consensus stops are logged. Cluster size, voter set and whether quorum was lost need the cluster topology at 17:38.
  3. 3.
    The failing meta-op is unknown. Payload-index operations are a hypothesis. We need the full error chain (the {err:#} context) from the two log lines.
  4. 4.
    Collection apply keeps failing. R2 keeps Raft alive; it does not let the state machine progress. If the full disk lasts longer than the reserve's ride-through time, the node falls into R3.
  5. 5.
    Dev differs from the incident build. Dev restarts consensus with backoff and changed DiskUsageWatcher caching. The incident build stops consensus permanently. Any backport decision must account for this.
  6. 6.
    Not designed for: EDQUOT (whether preallocated blocks stay charged to quota and keep later overwrites from failing is unverified), inode exhaustion (R1 removes the per-save inode need, but pool refill creates tmp-* files), read-only remount and EIO.
  7. 7.
    Collection WAL impact. If Materialize reached collection WALs by mistake, disk usage would jump. The option must default to Sparse and be covered by T1.
  8. 8.
    Raft state size growth past the slot size S_slot blocks saves. Slot size must be monitored, and resizing needs a migration step with the same publish protocol as Section 6.1.4.
  9. 9.
    Recycle write cost. Each recycle rewrites a full segment (32 MiB by default). That is rare for the consensus WAL, but should be measured.
  10. 10.
    Backfill cost and startup time. Backfill reads every open-* file on each start in Materialize mode ((1 + P) × C). It should be measured; if it matters, a persisted per-segment "materialized" marker could skip it, at the cost of one more piece of on-disk state to keep crash-safe.
  11. 11.
    Refusing to start in best_effort. Six cases refuse to start even in best_effort (Section 6.6). The precheck in migration step 2 makes the P? case rare, but a node on a failing filesystem can still be kept down by it, or by the C case on a pre-JSON node. The startup state write (slot barrier or JSON rewrite) keeps a node down whose disk cannot hold one more state file. This is chosen over any path that could roll back term or vote.
  12. 12.
    Pre-existing truncation durability gap. Source reading (Section 6.1.2.1) indicates that the flush after Segment::truncate does not sync the zeroed range, and that today's suffix truncation deletes closed segments head-first without directory syncs. A crash can then bring removed entries back, in the worst case placed after a shorter closed set at a wrong WAL index. This affects collection WALs and the consensus WAL in off mode, which this design does not change. It is not reproduced yet (T4f). If T4f confirms it, it should be fixed separately for Sparse mode, independent of the reserve.
  13. 13.
    Availability cost of the detach latch. After one durability unknown rename, the consensus WAL accepts no structural change until the process restarts (Section 6.1.2), so the node falls into R3 once its open segment fills or the leader needs a structural truncation. This is chosen over trusting a later directory fsync within the process. B1/T2c may allow a narrower rule.
  14. 14.
    Recovery barrier cost and scope. The barrier (Section 6.4.1) rewrites the used part of every retained segment and writes two state slots at every start and after every flush error. During a long apply pause the retained log can be many segments, so startup and rejoin get slower exactly when the disk is full. It must be measured. The barrier also does not cover off mode: today's code, and off mode in this design, rebuild Raft from a reopened file after a flush error with the same page-cache hazard. That is a pre-existing gap, like risk 12, and should be fixed separately.
  15. 15.
    Sizing depends on the entry cap E_cap. The worst-case bound in Section 6.5 holds only for entries within E_cap, and it is enforced only at proposal time. Over-cap entries that still arrive are safe (exact admission) but shorten the ride-through, and the alert reports them. With E_cap close to U / 2 or above, the bound is one segment per entry, which may make a useful ride-through time impractical with 32 MiB segments. Open: which E_cap is acceptable for every ConsensusOperations variant (large collection configs, shard-key mappings, cluster metadata). An operation that exceeds it would need to be split or rejected. Also open: how to roll out the cap in a mixed-version cluster, where older leaders do not enforce it.
  16. 16.
    Three-slot state protocol is new and only argued, not checked. The keep-set rule (Section 6.1.3) replaces revision 4's in-place rewrite. Its safety argument is a hand proof over the rules. T3e includes a bounded exhaustive check, but a bounded check does not cover every sequence, and the proof has not been independently reviewed. The rule also adds two slot writes to every barrier pass, and S_slot worth of reserve.
  17. 17.
    The Json backend is a second state path. A best_effort node whose migration is skipped runs on JSON with its own save sequence, latch and barrier arm (Section 6.1.5). It has no state reserve, so on a full disk it reaches R3 on its first state save, and it depends on B1 for every rename. It doubles the state-persistence code that needs tests (T3f). The alternative, refusing to start whenever migration cannot complete, was rejected: with best_effort as the default (Section 6.6), every node on a filesystem without fallocate would fail to start.
  18. 18.
    best_effort unreserved WAL path. A degraded best_effort node appends into ordinary free space (Section 6.5). Where fallocate works, the guard rejects cleanly on a full disk. Where it does not (tmpfs, overlay and network filesystems, Section 5.4), a store into a hole can terminate the whole process, and the node can crash-loop while the disk stays full. That matches today's off behavior on the same filesystem, but it is an availability cost that only the alert in Section 6.6 makes visible. The path also inherits today's unverified assumption that a successful msync means the bytes are durable, which T2f checks for holes. If T2f fails, the fallback becomes fail-closed: such a node cannot append past its reserved space. With zero reserve that means no appends at all, so it goes to R3 at its first append after startup. The open question then is whether best_effort should still be the default on filesystems without fallocate (Section 6.6, rollout step 3).
  19. 19.
    Preflight assumes contiguous batches. Admission simulates a conflict truncation only at the first entry of a batch (Section 6.5). That is exact only if raft-rs hands append_entries contiguous entries, which this document did not line-check in raft-rs. A non-contiguous batch is rejected before mutation, so the assumption affects availability, not safety: if raft-rs ever produced one, the node would stop and rebuild on that batch. T11c checks it on a cluster. The preflight also moves today's per-entry checks ahead of every mutation, which changes when some errors are returned (before the first append, not after earlier ones).
