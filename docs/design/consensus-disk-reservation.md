## 1. Summary

**R1 does not address the incident by itself.** Both pods that logged `Consensus stopped with error` did so with the collection disk-guard message `No space left on device: WAL buffer size exceeds available disk space`. The guard fires when free space drops below `2 × wal_capacity_mb` of the collection (64 MiB with the default 32 MiB, `local_shard/mod.rs:277-283`, `shard_ops.rs:83-96`). Consensus stopped because applying a committed meta-operation returned a `ServiceError` (`consensus_manager.rs:448-452`), not because a consensus write failed. The fix for that path is R2, which needs no filesystem assumptions and can ship first.

R1 covers the harder case where the volume reaches zero free bytes. Today a Raft state save creates a new file and renames it (`persistent.rs:398-407`), and consensus WAL segments are sized with `ftruncate` (`segment.rs:174`), which reserves no blocks. On a full volume both can fail, and the node stops voting and replicating even if R2 is in place. R1 preallocates a small, fixed amount of real blocks so that the node can keep persisting Raft log entries and state for a limited time after the volume is full.

**Phase 1 proposal (this document):**

1. Consensus WAL segments are materialized when they are created: `fallocate` mode 0, then zeros written and synced. Collection WALs are unchanged.
2. The WAL keeps `P` materialized spare segments, created at startup and refilled in the background from ordinary free space.
3. Segment deletion stays as it is today. Compaction and truncation still delete segments. There is no recycling.
4. The Raft state moves from `raft_state.json` to a fixed-size, materialized two-slot file that is overwritten in place. A node migrates only after a cluster-wide cap on user-controlled cluster metadata has been activated through consensus and its own map is within that cap (Section 6).
5. When the open segment and the spares are used up, the next append fails and the node fails closed: it sends no persisted messages, reloads its consensus state from disk, and retries with today's backoff until space returns.

**Guarantee boundary.** No guarantee is claimed yet. The design target is: on a node whose reserve is materialized, on a filesystem where B1 holds, after ordinary free space reaches zero, consensus WAL appends and state saves keep succeeding until the open segment and the `P` spares are full. After that the node behaves like today's code on a full disk, only later. R1 does not make collection meta-operations succeed, and it does not protect collection data, collection WALs, optimizer output, snapshots, or segment-state and ID-tracker flushes.

**Out of scope:** sync errors (Section 5), inode exhaustion, `EDQUOT`, read-only remounts, and startup panics in shard loading.

## 3. Storage Paths

| Path | Files | Write mechanism today | R1 |
|---|---|---|---|
| Consensus WAL (`ConsensusOpWal`) | `<storage>/collections_meta_wal/open-N`, `closed-N` | `lib/wal`: `ftruncate`, `mmap`, `msync`; retire renames `open-N` to `closed-N` | Segments materialized; `P` spares |
| Raft state (`Persistent`) | `<storage>/raft_state.json` | `AtomicFile`: temporary file, write, rename | Two-slot file, overwritten in place |
| Collection WAL, segments, optimizer output, segment state, ID tracker, snapshots | per collection and shard | various | Not covered |

The consensus WAL and collection WALs share `lib/wal`. R1 must be an explicit `WalOptions` choice used only by `ConsensusOpWal::new` (`consensus_wal.rs:28-46`, which calls `Wal::open` with defaults today). Otherwise every collection shard would pin real blocks for each segment.

The reserve does not help the collection guard. Materialized blocks are not part of free space as `statvfs` reports it, so the collection guard and the quota manager see free space drop by about the size of the reserve. Nothing is double-counted. While free space is below the guard threshold, every meta-operation that writes collection data keeps failing.

## 4. Design

### 4.1 Materialized Segments and Spares

- **Option.** Add `WalOptions::allocation: Sparse | Materialize`. Collection WALs keep `Sparse`. `ConsensusOpWal` uses `Materialize` when `consensus.reserve.mode` is `best_effort`.
- **Create.** `Segment::create` keeps its structure (`segment.rs:127-217`): build `tmp-<name>`, then rename. In `Materialize` mode it replaces `ftruncate` with `fallocate` mode 0 over `[0, C)`, `pwrite` of zeros over `[0, C)`, the header, and `fdatasync`. The rename and the directory sync follow as today (`segment_creator.rs:32-58`). A crash before the rename leaves `tmp-*`, which `Wal::open` deletes (`wal/lib.rs:564-567`).
- **Pool.** `segment_queue_len` is set to `P` (today 0, clamped to 1, `segment_creator.rs:97`). The pool is created at startup. Refills run on the existing background thread (`segment_creator.rs:107-123`), and a refill failure lowers the reserve metric without failing an append.
- **Creator restart after a failure.** Today `refill_pending` takes the creation thread, returns its error, and `next` returns `no segments available` without calling `schedule_creation` again (`segment_creator.rs:125-150`). After one failed creation, the creator never creates another segment for the life of the `Wal`. R1 needs the creator to reschedule after a failure, with backoff, so that the node recovers when space returns. This is a pre-existing gap found by source reading, not reproduced (follow-up F2).
- **Fallback.** If `fallocate` returns `EOPNOTSUPP`, the creator falls back to today's `ftruncate` creation, and the segment counts as zero reserve. The node is reported `degraded`. On `ENOSPC` it does not fall back, because a sparse segment would fail on its first store, and the refill is retried later.
- **Oversized entries.** `ensure_capacity` grows a segment for an entry larger than its capacity (`segment.rs:495-526`). In `Materialize` mode that growth returns an error, and the append fails as in Section 4.3. To keep this off the normal path, proposals larger than `E_cap` are rejected before `propose`, with `footprint(E_cap) ≤ U` (Section 6).
- **Deletes stay.** `prefix_truncate`, `Wal::truncate` and the retire-time removal of an empty closed segment keep deleting files (`wal/lib.rs:285, 351-402, 410-445`). Their blocks return to the shared pool, so on a volume that stays full the reserve is consumed once, never reused.

**Upgrade.** `Wal::with_options` reopens the files an older binary created with `ftruncate`. In `Materialize` mode, before mapping them: an empty `open-*` spare gets `fallocate` over `[0, len)`, zeros written over `[8, len)` and `fdatasync`. That is safe because it holds no entries and those bytes already read as zero. The active non-empty `open-*` gets `fallocate` over `[0, len)` only, which allocates holes and leaves existing data unchanged. Whether a range that was only `fallocate`d needs metadata on its first write is part of B1, so the active segment counts as zero reserve until it retires. Any error leaves the file as it is, counts it as zero reserve, and reports `degraded`.

### 4.2 Two-Slot Raft State File

- `raft_state.slots` is a materialized file of `2 × S_slot` bytes. Each slot holds a magic, a format version, a `u64` generation, the payload length, the payload (today's JSON serialization of `Persistent`), and a `crc32c` over all of these.
- **Save:** serialize the state. If it is larger than `S_slot` minus the header, return an error before writing. Otherwise `pwrite` the slot that does not hold the newest valid generation, with generation `N + 1`, then `fdatasync`. No new file, inode or rename. A save is allowed only once the file is *confirmed* (next bullet); before that it returns an error without writing.
- **Load and confirm.** Read both slots, ignore any with a bad magic or CRC, and select the newest valid generation. If neither is valid, refuse to start. Falling back to JSON could roll back term and vote. Selecting a slot is not enough: a process killed after the full `pwrite` of generation `N + 1` and before its `fdatasync` leaves `N + 1` visible in the page cache while only `N` is on disk, and no sync error is involved. If the next save overwrote `N` and power was lost before `N + 1` was written back, no valid slot would remain on disk. So the loader runs a **confirmation step** before it returns: `fdatasync` the slot file, then read the selected slot again and re-check its magic, CRC and generation. Only then is the file confirmed and `save()` enabled. Until confirmation succeeds, the process sends no consensus message and overwrites no slot, so the older generation stays on disk unchanged. If the confirming `fdatasync` or re-check fails, the node fails closed under the Section 5 policy: it sets the `consensus_storage_failed` latch, does not start consensus, and reports the failure; a process restart is required. This applies to every load of `raft_state.slots`: at startup in `load_or_init` (Appendix A), and in the Section 4.3 rebuild, which loads a new `Persistent`.
- **Mutate after save.** `apply_state_update` assigns `self.state` before `save()` (`persistent.rs:214-222`). The new code builds the next state, saves it, and only then assigns it. The same rule applies to `entry_applied` and `set_unapplied_entries` (`persistent.rs:228-240`).
- **Crash safety.** Invariant: a save overwrites a slot only while the other slot holds a generation whose `fdatasync` returned success in this process, either in the confirmation step or in an earlier save. Saves are sequential, and a save's `fdatasync` completes before the next save starts, so the invariant holds for the life of the process. A torn write therefore damages only the target slot, and the other slot's generation is on disk. This argument covers crashes, including a kill between `pwrite` and `fdatasync` followed by a restart. It does not cover a failed `fdatasync` whose bytes remain visible in the page cache (Section 5).
- **Migration** from `raft_state.json` (and the legacy CBOR file) runs once at startup while free space exists. Its states and restart rules are in Appendix A. The rule that makes it safe: `raft_state.slots` appears under its final name only with a valid slot, and once the publish rename returns success the process never writes JSON again.
- **Fallback.** If the slot file cannot be materialized (`EOPNOTSUPP`, or too little free space), or the cluster metadata gates of Section 6 are not met (no activation record yet, a map still over `M_meta`, or an `S_slot` below the sizing bound), the node stays on today's JSON save path, unchanged, and is reported `degraded` with the reason. It has no state reserve. The gates are re-checked after each applied cluster metadata entry, and the migration then runs online (Section 6, rollout gate 2).

### 4.3 Exhaustion and Recovery (R3, Fail-Closed)

1. **Exhaustion.** An append needs the next segment, and the creator has no spare. `creator.next()` returns an error (`segment_creator.rs:142-150`), so `Wal::append` and `append_entries` return `Err`. The same happens for an oversized entry, and for a state save whose payload does not fit in a slot.
2. **No persisted message.** `process_ready` propagates the error before persisted messages are sent (`src/consensus.rs:1123-1130`). This is today's behavior on a full disk, reached later.
3. **Reload, not reuse.** Earlier entries of the failed batch may already be in the in-memory WAL index without a flush (`segment.rs:373` before `:421-448`). Today the rebuild reuses the in-memory `Persistent` and `ConsensusOpWal` (`src/consensus.rs:198-209`). In R1 the rebuild instead runs the recovery pass below, and only then builds a new `RaftNode`. The same pass runs at startup, where steps 3a and 3b are today's `load_or_init` and `ConsensusManager::new`. If any step fails, the node stays fail-closed and reports `consensus_recovery_blocked`. It never moves `commit` or `applied` to repair the state.
   - **3a. Reload and sync.** Load `Persistent` and the WAL from disk again (a new `Wal` instance, which also gets a new creator). Confirm the state file (Section 4.2) and `fdatasync` every retained segment. The sync matters because the reloaded bytes may never have been synced. When no sync error has happened in this process, a successful `fdatasync` makes them durable under today's ordinary assumption. The state must be durable before step 3b reads it, or a power loss after the clear in 3b could leave the pre-snapshot state on disk with its entries already gone.
   - **3b. Snapshot reconciliation, before any bound check.** `update_from_snapshot` sets `hard_state.commit = latest_snapshot_meta.index` and saves both in one write (`persistent.rs:68-109`), and `apply_snapshot` clears the WAL only afterwards (`consensus_manager.rs:791`). A crash, or a failed `wal.clear()`, between the two leaves a durable state whose `commit` legitimately exceeds the WAL's last index. Today `ConsensusManager::new` repairs this at startup (`consensus_manager.rs:127-146`): if `commit == latest_snapshot_meta.index` and the last WAL entry has `index < latest_snapshot_meta.index`, the WAL is cleared. In R1 this check runs at startup, as today, and also on every rebuild, because a rebuild after a failed `wal.clear()` inside `apply_snapshot` reaches the same state without passing through `ConsensusManager::new`. Two differences from today's code: an error from `last_entry()` or from the clear fails the pass instead of silently skipping the check (today's `let Ok(Some(last))` skips on error), and the clear is followed by a WAL directory `fsync`. The clear itself is today's `ConsensusOpWal::clear`, which is `Wal::truncate(first_index)` plus a flush (`consensus_wal.rs:48-53`, `wal/lib.rs:500-502`). It keeps the F1 limitations (Section 9): a crash in the middle of its head-first deletes can leave a segment gap that the next reopen rejects with `missing segment(s)`. That outcome is fail-closed, not unsafe, and goes away with the F1 fix. A stale WAL whose last entry is at or above the snapshot index is not cleared, as today; raft-rs resolves such entries through the leader's conflict truncation.
   - **3c. Bounds.** `snap = latest_snapshot_meta.index` (0 if no snapshot was ever installed), `applied = last_applied_entry()` or 0, `commit = hard_state.commit`. For a non-empty WAL, `first` and `last` are the Raft indices of its first and last physical entries; right after a reload `compacted_until_raft_index` is 0 (`consensus_wal.rs:44`), so `first_entry` and `last_entry` return physical entries. For an empty WAL, `first = snap + 1` and `last = snap`, which is what the `Storage` implementation answers raft-rs (`consensus_manager.rs:1389-1402`). The checks are `commit ≤ last`, `applied ≤ commit`, and `first ≤ applied + 1` (compaction stops at the last applied entry, `consensus_manager.rs:1109-1136`). After a snapshot install with a cleared or empty WAL, `commit = applied = snap = last`, which passes. A WAL with `last < snap` but `commit > snap` is blocked, because committed entries after the snapshot are missing.
4. **Retry.** While the volume stays full, the next batch fails again. The node behaves like a crashed follower and retries with today's backoff. When space returns, the creator refills the pool and the node rejoins.
5. **No pre-mutation admission in phase 1.** A check that rejects a batch before any mutation needs to model conflict truncation and segment placement exactly. Phase 1 relies on the error path above instead. Such a check can be added later if measurements show that the reload is too expensive.

### 4.4 Configuration, Metrics, Rollout

- `consensus.reserve.mode: off | best_effort`. `off` is today's behavior. `best_effort` materializes, migrates and falls back as described above. It does not refuse to start because of the reserve, except in the migration cases of Appendix A. An `enforce` mode, which refuses to start without a full reserve, is deferred until a filesystem passes Section 8.
- `consensus.reserve.spare_segments` (`P`), `consensus.wal_segment_capacity_mb` (`C`, Section 6), `consensus.max_entry_bytes` (`E_cap`), `consensus.state_slot_bytes` (`S_slot`).
- Optional `consensus_storage_path` for a dedicated volume. A dedicated volume also isolates inodes, directory entries and journal from collection writers. It is the answer if B1 fails.
- Metrics: reserve bytes total and free, `spares_materialized`, `degraded` (with its reason), `consensus_state_backend` (`json` or `slots`), `consensus_recovery_blocked`, `consensus_storage_failed` (Section 5), `cluster_metadata_cap_active`, `cluster_metadata_cap_violation` (Section 6), filesystem type (`statfs` `f_type`). Alerts: spares below `P`, `degraded` at startup, any `consensus_storage_failed`, any `cluster_metadata_cap_violation`.
- Rollout: telemetry for entry sizes, commit rate and state size first; then `best_effort` on canary clusters; defaults after Section 8 evidence. The WAL reserve takes effect per node as soon as the mode is on. The state slot backend takes effect per node only after the cluster metadata cap activation record is committed and that node's map is within the cap (Section 6), so a rolling upgrade first completes, then the cap activates on its own, then nodes migrate. Rollback needs a downgrade tool that writes the **current** slot state back to `raft_state.json` and then renames `raft_state.slots` away (Appendix A); it refuses to run while an activation record is present unless forced, because the downgraded node would apply metadata updates without the cap. Older binaries cannot read the slot file.

## 5. Sync Errors: Out of Scope, Fail-Closed

After `msync` or `fdatasync` fails, the page cache can still show bytes that never reached disk, and a later sync on a new handle may succeed without writing them. Fixing that needs a design that covers every Qdrant file: collection WALs, segments, and `off` mode have the same exposure today. This proposal does not attempt it, so it claims nothing about durability after a sync error. It also does not let the error path make things worse:

- Any `msync`, `fdatasync` or `fsync` error on a consensus WAL segment, the WAL directory, or the state file sets a process-wide latch. The consensus thread then stops without a rebuild, sends no further messages, makes no further consensus writes, and reports `consensus_storage_failed`. Collection serving continues.
- Recovery requires a process restart. A restart without a reboot can still read bytes that exist only in the page cache, exactly as today. Neither reopening nor retrying is treated as proof of durability.
- So the design has no sync-error recovery barrier, no third state slot and no keep set: they would address only this case. The slot confirmation step of Section 4.2 and the reload, sync and index checks of Section 4.3 remain, because they address bytes that were written but never synced, which happens after a plain kill without any sync error.

## 6. Sizing

Inputs (measured or chosen; this document assumes none of their values):

- `E_cap`: maximum encoded consensus entry, enforced at proposal time. `F_max = footprint(E_cap)`, where `footprint(len) = 8 + len + padding(len) + 4` and `padding(len) = (4 - len) mod 8` (`segment.rs:22-26, 691-693`).
- `C`: consensus WAL segment capacity, chosen for the consensus WAL independently of the collection `wal_capacity_mb`. `U = (C & !7) - 8` is the usable bytes per segment (`segment.rs:144`).
- `P`: materialized spares. `R`: committed entries per second while the volume is full. `S_obs`: largest serialized `Persistent`.

**Choosing `C`.** Constraint: `F_max ≤ U`, so that no entry needs segment growth. Larger `C` gives each segment more ride-through but pins more blocks and costs one larger zero write per created segment. Smaller `C` causes more retire renames, which are B1 operations on a full disk. Entries are never split across segments (`wal/lib.rs:294-308`), so a segment holds at least `k = floor(U / F_max)` entries. The default for `C` is chosen together with `E_cap` from telemetry. Each segment's capacity is its file length (`segment.rs:231`), so a changed `C` applies to new segments only.

**Ride-through.** With `r` bytes left in a reserved open segment, the worst-case number of entries that still fit is `floor(r / F_max) + P × k`. The time is that count divided by `R`. With a realistic mean footprint the count is much larger, but only the worst case is a bound. To plan for a backlog of `N` entries, choose `P ≥ ceil(N / k)`.

**State slot size.** `S_slot` must bound the serialized `Persistent`, which includes the peer address book, peer metadata, and `cluster_metadata: HashMap<String, serde_json::Value>` (`persistent.rs:50`). Cluster metadata is user-controlled through `PUT /cluster/metadata/keys/{key}` (`cluster_api.rs:155-176`, applied at `consensus_manager.rs:672-678`). Each value is limited only by the request size (`max_request_size_mb`, 32 by default), and the number of keys is not limited. Without a bound, a user can make every state save fail and keep the node in R3. Proposal: a cap `M_meta` on the cluster metadata map, defined, activated cluster-wide, and enforced as follows.

- **Definition.** `meta_bytes(map)` is the exact length of the compact `serde_json` encoding of the map, which is how it appears inside the slot payload. The length does not depend on the `HashMap` iteration order, because each entry contributes its own encoded key, value and separator. It does depend on `serde_json` producing the same encoding for the same value on every replica, which holds for one `serde_json` version; a dependency change that alters the encoding (number formatting, for example) must be treated as a cap change (below). The cap is `meta_bytes(map) ≤ M_meta` for the applied map on every peer.
- **Activation record.** The cap is not enforced from a build-time constant. It is enforced from an *activation record* `{cap_version, M_meta}` that is part of the applied state: a new field of `Persistent`, saved with the state, mirrored in the shadow `ClusterState`, and carried in the Raft snapshot as a new optional `SnapshotData` field with `#[serde(default)]`, as `quota_config` already is (`consensus_manager.rs:59-69`). Without a record, no peer enforces anything at apply time, which is today's behavior. The record is set by a committed entry of a new variant, `ConsensusOperations::ActivateClusterMetadataCap { cap_version, M_meta }`. Every replica reads `M_meta` from the applied record, never from its own binary, so the enforced value is identical on every replica for the same reason that any applied state is. The build-time constant is only the value that a proposer writes into the entry.
- **Activation barrier.** The *members* at a log index are the peer IDs in the applied `conf_state` at that index: `voters`, `voters_outgoing`, `learners` and `learners_next`. `V_cap` is the first release whose binary has the apply-time check and decodes the activation entry. The barrier holds at an index when every member has an entry in the applied address book and an entry in the applied `peer_metadata_by_id` whose version, compared on major, minor and patch with the pre-release part ignored, is at least `V_cap`. All three inputs are functions of the committed log prefix: `conf_state` changes only through conf-change entries (`consensus_manager.rs:523-527`); the address book changes through the `AddPeer` and `RemovePeer` handlers of those entries; and `peer_metadata_by_id` changes only through `UpdatePeerMetadata` entries, which a peer proposes about itself with its own running version (`consensus_manager.rs:1141-1162`, every 60 s while its entry is outdated, `:56`), and through peer removal (`:897`, `action_applier.rs:27`). Snapshots carry all three (`persistent.rs:68-109`). The address-book condition is there because `load_or_init` drops metadata of peers that are not in the address book (`persistent.rs:193-198`); without that condition a restarted replica and a running replica could evaluate a member that is in `conf_state` but not in the address book differently. So every replica evaluates the barrier identically at every index. The barrier uses the version that `PeerMetadata` already carries (`types.rs:1967-1970`) and not a new capability field, because an older binary re-serializes `PeerMetadata` without fields it does not know: a snapshot served by an older leader would drop a new field, and replicas that installed that snapshot would evaluate the barrier differently from replicas that applied the log. The version field round-trips through every supported binary.
  - *Offline and stale members.* An offline member counts with the version it last advertised. If that is at least `V_cap`, it supports the cap. If it is lower or absent (a member that never advertised, or one that was just added), the barrier does not hold until that member is upgraded, started and has advertised, or until it is removed with `RemovePeer`. There is no way to satisfy the barrier on behalf of another peer: only the peer itself proposes its version.
  - *Dev builds.* Ignoring the pre-release part makes `1.X.0-dev` count as `1.X.0`, so the consensus tests can activate the cap. A cluster that mixes dev builds from the same cycle with and without the feature is therefore not covered. That is not a supported upgrade path.
- **Proposing and committing the activation.** Any upgraded peer whose applied state satisfies the barrier and holds no record proposes the activation entry, throttled like `try_update_peer_metadata`. The proposer's view is only a hint. At apply, every replica evaluates the barrier again against the applied state at the entry's index: if the barrier holds and there is no record, it stores the record; if a record with the same `cap_version` is already present, the entry is an idempotent no-op, as `plan_update_cluster_metadata` treats an already-applied write (`state/plan.rs:1649`); if the barrier does not hold, the entry is rejected with `BadInput`, which the apply loop counts as applied with a user error (`consensus_manager.rs:454-461`), and the proposer retries later. Concurrent proposals are therefore harmless, and the decision is the same on every replica because its inputs are. The shadow state machine plans the same outcome. No operator action is needed beyond completing the upgrade or removing dead members. The record is reported by the `cluster_metadata_cap_active` metric.
- **Older binaries after activation.** An older binary cannot decode the activation entry: `ConsensusOperations::try_from` fails (`consensus_manager.rs:624`), the error maps to a `ServiceError` (`errors.rs:317-321`), and consensus on that peer stops (`:448-452`). That is the intended outcome for a member that was downgraded after advertising `V_cap` and catches up through the log: it fails closed instead of applying what upgraded replicas reject. A downgraded member that catches up through a snapshot, or an older binary added as a new peer after activation, does not stop: it ignores the record field and applies metadata updates unconditionally. Both are operator actions, and both are **unsupported** after activation, in the same way that running an older binary on a migrated state file is unsupported (Appendix A). Upgraded peers detect them from the member's next advertised version and report `cluster_metadata_cap_violation`, and the downgrade tool refuses to run while a record is present unless forced. A record is never removed by the log, so the barrier cannot be undone.
- **Changing the cap.** Not designed here. A second activation with a higher `cap_version` needs the same barrier for the binary that introduces it, and a larger value also needs every node's `S_slot` to satisfy the sizing inequality below before any node is on slots with the new value. Until that exists, the value in the first record is the value.
- **Authoritative check at apply time.** With a record present, the check runs on every replica inside the apply of `UpdateClusterMetadata`, before `update_cluster_metadata_key` mutates the map (`persistent.rs:292-298`, called from `consensus_manager.rs:672-678`). Let `cur = meta_bytes(applied map)` and `proj = meta_bytes(projected map)`, where the projected map is the applied map with the key inserted, or removed for a null value. The rule, evaluated top to bottom:

  | Case | Outcome |
  |---|---|
  | Projected map equals the applied map (a repeated write, or a delete of an absent key) | Accepted as a no-op, which is what the shadow plan does today (`state/plan.rs:1649`) |
  | `proj ≤ M_meta` | Accepted |
  | `cur > M_meta` and `proj < cur` | Accepted: the map is over the cap and the update strictly reduces its exact serialized size |
  | Otherwise | Rejected with `StorageError::BadInput` |

  The rejection is a user error: the entry counts as applied with an error, consensus moves on, and the proposer's waiter receives that error (`consensus_manager.rs:454-461`, `:638, 646-654`). The shadow state machine's `plan_update_cluster_metadata` returns `ApplyOutcome::Rejected` in the same cases (`consensus_state_machine/mod.rs:108-111, 412-418`), so the two agree. The check is deterministic because every replica applies the same log prefix to the same map with the same record, so no two replicas can disagree about the result. The third row exists for maps that are already over the cap when the record is applied, which today's API allows. A deletion always strictly reduces the size, so a map that needs several removals is repaired one key at a time, and a replacement is accepted while over the cap only if the new value is shorter. Once the map is within the cap, only the second row can accept, so the map never grows past `M_meta` again.
- **Pre-proposal check, an optimization only.** `TableOfContent::update_cluster_metadata` (`toc/mod.rs:639-665`) may run the same rule before proposing, to fail fast. It is not sufficient on its own: two concurrent requests to distinct keys can each pass against the same applied map and together exceed the cap once both commit, and a request that reaches an older peer is never checked. If kept, it must count the proposals that are in flight (accepted by this check but not yet applied) toward the projected size, and it must not be the only check.
- **Rollout gates.** Three conditions decide what a node does, and they are the only rollout conditions in this design:
  1. *Enforcement* at apply happens on a replica only when its applied state holds the record. Before that, during a rolling upgrade, every peer applies metadata updates unconditionally and the maps stay identical. The pre-proposal check on upgraded peers rejects oversized requests that reach them but cannot stop proposals through older peers, which is why enforcement waits for the record and not for the upgrade.
  2. *Slot migration* (Section 4.2, Appendix A step 2) requires, in addition to the free-space and `fallocate` checks, that the applied state holds the record, that `meta_bytes(applied map) ≤ M_meta`, and that the configured `S_slot` satisfies the sizing inequality below with the applied `M_meta`. A node that fails any of these stays on today's JSON backend, reported `degraded` with `consensus_state_backend = json` and the failing reason, and has no state reserve. The JSON path never fails closed because of the map. The check runs at startup in `load_or_init`, and again after each applied `UpdateClusterMetadata` or activation entry, under the `Persistent` write lock that every save already takes; when it passes, the migration runs online with the same Appendix A steps 3 to 6, and the rule that no JSON write follows a successful publish rename is unchanged.
  3. *WAL materialization* (Section 4.1) is independent of the cap and is gated only by `consensus.reserve.mode`.
- **Sizing.** The slot payload is the compact JSON of `Persistent`, so its length is `S_base + S_peers + S_meta`, where `S_base` is the encoding of the hard state, snapshot metadata, apply queue, first voter, peer ID and activation record (a few hundred bytes, measured as `S_obs` with an empty map and the current peer set), `S_peers` is the address book plus peer metadata (one URI and one version string per peer, so it grows with the peer count and address length, which operators control, not users), and `S_meta ≤ M_meta + δ`, where `δ` is the constant cost of the field name and separators (`"cluster_metadata":` and a comma). The requirement is `S_slot ≥ H_slot + S_base + S_peers_max + M_meta + δ`, with `H_slot` the slot header and `S_peers_max` the bound chosen for the peer set from telemetry with an explicit margin. There is no multiplier: a save larger than the slot fails closed (Section 4.3), so the bound has to be an actual bound, and any headroom is stated as `S_peers_max`. A node on slots got there only through gate 2, so its map is within `M_meta` and can only shrink or stay within it; the only way its state can outgrow the slot is a peer set beyond `S_peers_max`.
- **Relation to `E_cap`.** A single `UpdateClusterMetadata` entry carries one key and one value, so a value is admitted only if the entry fits in `E_cap` (checked at proposal time, Section 4.1) and the projected map fits in `M_meta` (checked at apply time). The two bounds are independent, and the largest value that can ever enter the map is bounded by both. Telemetry should confirm that this covers actual use.

An open question for review is whether cluster metadata should instead move out of the slot payload into its own file.

**Reserve bytes.** `(1 + P) × C + 2 × S_slot`.

**Cost of apply-progress saves.** `entry_applied` saves the full state after every applied entry, and `set_unapplied_entries` saves it once per committed batch (`persistent.rs:228-240`, `consensus_manager.rs:489-492`). With slots, each save is one `pwrite` of the serialized state (at most `S_slot`, rounded up to the filesystem block) plus one `fdatasync`. A batch of `n` committed entries therefore costs `n + 1` slot writes and `fdatasync`s, plus the hard-state and commit-index saves. Today each save creates, writes and renames a temporary file. Whether `AtomicFile` (`atomicwrites` 0.4.4) syncs is not verified here, so the relative cost must be measured before the defaults are chosen. Coalescing apply-progress saves per batch is possible but changes what a crash re-applies, and is not proposed here.

## 8. Evidence Required Before Agreement

- **B1 (unverified).** Whether retire renames, directory `fsync`s, slot overwrites and first writes into `fallocate`d ranges can fail with `ENOSPC` on ext4 and XFS once the reserve is materialized and free space is zero. `rename(2)` and `fsync(2)` document `ENOSPC`. `fallocate(2)` guarantees only that writes into the range do not fail "because of lack of disk space". It says nothing about metadata or the journal. T2 and T2b answer this. **They have not been run, and this revision does not run them.** If B1 fails, the options are a dedicated volume or a different WAL format (Appendix B). R1 on a shared volume would then not be worth shipping.
- **Ride-through measurement.** Real entry-size distribution, `R` during incidents and `S_obs`, to decide whether the open segment plus `P` spares gives a useful ride-through. If it does not, recycling becomes the next phase (Appendix B).
- **Apply-progress save cost** (Section 6).
- Until these exist, no current agreement, guarantee or production-readiness claim applies to this proposal.

## 9. Pre-Existing Issues Found (Separate Follow-Ups)

These were found by source reading and are not reproduced. Each should be a small, separate fix. None is implemented here.

- **F1. `Wal::truncate` deletes closed segments head-first without a directory sync** (`wal/lib.rs:364-397`). A crash after a lower segment's delete has reached disk, and before a higher one's has, leaves a gap, and `Wal::with_options` then fails with `missing segment(s)` (`wal/lib.rs:177-210`). Fix: delete tail-first, with a directory `fsync` after each delete. A related detail: the zeros that `Segment::truncate` writes are not synced by the `flush` that follows (`segment.rs:405-418, 421-448`). When only the open segment is truncated, stale uncommitted entries can come back after a crash at the same indices, which Raft accepts. When closed segments are also removed, the open segment's stale entries can come back after a shorter closed set at a shifted WAL index (`wal/lib.rs:449-456`). The fix should therefore also sync the zeroed range of the open segment before the first delete. For the consensus WAL this needs more than one segment of conflicting entries, so it should be rare.
- **F2. The segment creator stops after one failed creation** (Section 4.1).
- **F3. A retired segment's tail is synced asynchronously.** `retire_open_segment` starts `flush_async` on the retired segment (`wal/lib.rs:270-276`) and joins it only at the next retire. `append_entries` flushes only the open segment (`consensus_wal.rs:259`, `wal/lib.rs:310-314`). When a batch crosses a segment boundary, persisted messages can therefore be sent before the retired segment's last entries are synced. If this is confirmed, `ConsensusOpWal` must wait for that flush before `append_entries` returns.

## Appendix A. State File Migration

Migration runs inside `load_or_init` (`persistent.rs:115-190`) before any `RaftNode` exists.

1. **Source.** Load `raft_state.json` if it exists. Otherwise, if only the CBOR `raft_state` exists, run today's CBOR-to-JSON migration (`persistent.rs:127-133`) and `fsync` the storage directory. For a new node, write the initial state (today's `init`, `persistent.rs:347-382`) as `raft_state.json` and `fsync` the directory. If that directory `fsync` fails, refuse to start, because the JSON name may not be durable.
2. **Precheck.** If free space is below `2 × S_slot` plus a margin, or `fallocate` is unsupported, or the loaded state holds no cluster metadata cap activation record, or its map is over the record's `M_meta`, or the configured `S_slot` is below the Section 6 sizing bound, stay on JSON (`degraded`, with the reason). The last three conditions are re-checked after each applied cluster metadata entry, and when they pass the migration continues from step 3 online, under the `Persistent` write lock (Section 6, rollout gate 2). Steps 3 to 6 are the same in both cases.
3. Create `raft_state.slots.tmp`, materialize it, write slot 0 with generation 1, `fdatasync`, and read it back to verify.
4. `rename(raft_state.slots.tmp, raft_state.slots)`. **After this call returns success, the process never writes JSON again.**
5. `fsync` the storage directory. If it fails, refuse to start. Both possible files hold the same state, and the restart rules handle either.
6. Cleanup: rename CBOR `raft_state` (if present) and then `raft_state.json` to `*.migrated`, each followed by a directory `fsync`. A failure here logs a warning and is retried at the next start.

Restart rules, checked in order after a storage-directory `fsync` (a failure refuses to start):

| Files | Action |
|---|---|
| `raft_state.slots` with a valid slot | Confirm it (Section 4.2), then use it. Delete `.slots.tmp`. Retry cleanup. Never read JSON or CBOR |
| `raft_state.slots` with no valid slot | Refuse to start |
| `.slots.tmp` and `raft_state.json` | Delete `.slots.tmp`, load JSON, migrate again |
| `raft_state.json` only (CBOR or `.migrated` may exist) | Load JSON, migrate |
| CBOR `raft_state` only | Step 1, then migrate |
| `.slots.tmp` or a `.migrated` file without `raft_state.json` and without `.slots` | Refuse to start. This cannot happen if directory `fsync` behaves as assumed |
| No state file | New node, step 1 |

The downgrade tool loads `.slots`, writes `raft_state.json` from the current slot, `fsync`s the directory, then renames `.slots` to `.slots.downgraded` and `fsync`s again. Starting an older binary on a migrated node without the tool is unsupported, because a leftover JSON file would be stale.

## Appendix B. Later Options, If Phase 1 Is Not Enough

Evaluate these only if Section 8 shows that phase 1's ride-through is too short or that B1 fails.

- **Fixed-name ring file for the consensus WAL.** One preallocated file with a small header and in-place, CRC-chained records, plus a durable head offset. It removes the retire rename and every per-segment rename or delete from the hot path, and it removes the need for a recycle protocol. The consensus WAL is its own `Wal` instance, so it can have its own format without changing collection WALs. This is the primary candidate.
- **Rename-based recycling** of retired segments through a staging name, with durability gates before content changes and before reuse. It keeps the current format but adds two renames and two directory `fsync`s per segment, which are exactly the B1 operations. It is not proposed.
- **Pre-mutation admission** that simulates placement after conflict truncation (Section 4.3, step 5).
- **A dedicated volume** (`consensus_storage_path`), which needs no new format and is the fallback if B1 fails.
